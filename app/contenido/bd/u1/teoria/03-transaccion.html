Definiciones

3. Transacción y sus propiedades

Para escribir en la hoja

Una transacción es un conjunto de operaciones sobre la base de datos (consultas, inserciones, modificaciones, eliminaciones) que se ejecutan como una sola unidad de trabajo: o se realizan todas, o no se realiza ninguna. Lleva a la base de un estado consistente a otro estado consistente.

Si todas salen bien, se confirma (COMMIT) y los cambios quedan guardados; si alguna falla, se deshace (ROLLBACK) y la base vuelve a como estaba antes de empezar.

Sus propiedades se conocen como ACID:

  • Atomicidad: la transacción es indivisible; se ejecuta completa o no se ejecuta nada.
  • Consistencia: deja la base en un estado válido, respetando todas las restricciones de integridad (claves, valores permitidos).
  • Aislamiento: las transacciones que se ejecutan al mismo tiempo no se interfieren; cada una trabaja como si estuviera sola.
  • Durabilidad: una vez confirmada, los cambios son permanentes, aunque después se corte la luz o falle el sistema.

Por qué hace falta

Muchas tareas de la vida real necesitan más de una sentencia, y si se corta en el medio, la base queda contando algo que no pasó. El ejemplo clásico es una transferencia bancaria:

  1. restar 1000 pesos de la cuenta A;
  2. sumar 1000 pesos a la cuenta B.

Si se ejecuta la 1 y el sistema se cae antes de la 2, desaparecieron 1000 pesos. Metidas en una transacción, las dos sentencias son una sola cosa: si la 2 no llega a hacerse, la 1 se deshace.

Cada propiedad, con quién se encarga

Los apuntes de la cátedra no listan las cuatro propiedades, pero sí nombran los módulos del SGBD que las cumplen. Sirve para ampliar la respuesta:

Las sentencias, en SQL Server

SentenciaQué hace
BEGIN TRANMarca el comienzo: desde acá, todo es parte de la transacción
COMMITConfirma: los cambios quedan guardados para siempre (durabilidad)
ROLLBACKDeshace: todo vuelve a como estaba en el BEGIN TRAN (atomicidad)

Son las mismas que se usaron en el Trabajo Práctico final: el script de carga empezaba con BEGIN TRAN, se revisaba el resultado con un SELECT y recién ahí se confirmaba con COMMIT; si algo había salido mal, se volvía atrás con ROLLBACK.

Ejemplo 1: la transferencia

Pasar 1000 pesos de la cuenta 10 a la cuenta 20 sin riesgo de que la plata se pierda.

BEGIN TRAN;
UPDATE Cuenta SET Saldo = Saldo - 1000 WHERE Numero = 10;
UPDATE Cuenta SET Saldo = Saldo + 1000 WHERE Numero = 20;
COMMIT;
  • Si el sistema se cae entre los dos UPDATE, nunca llegó el COMMIT: al volver, el SGBD deshace el primero. Atomicidad.
  • Si otra persona consulta el saldo justo en el medio, no ve la cuenta 10 ya descontada y la 20 sin sumar. Aislamiento.
  • Después del COMMIT, aunque se corte la luz, la transferencia queda hecha. Durabilidad.
  • La plata total antes y después es la misma: la base sigue siendo correcta. Consistencia.

Ejemplo 2: con el caso del parcial

En la clínica veterinaria, cuando un turno se atiende hay que hacer dos cosas: registrar la consulta y cambiar el estado del turno a "Atendido".

BEGIN TRAN;
INSERT INTO Consulta (Numero, Diagnostico, Observaciones, Fecha, NumeroTurno)
VALUES (501, 'Otitis', 'Control en 7 días', '2026-10-14', 3020);
UPDATE Turno SET Estado = 'Atendido' WHERE Numero = 3020;
COMMIT;

Sin la transacción, si el UPDATE falla quedaría una consulta registrada para un turno que sigue figurando como "Pendiente". Con ella, o quedan las dos cosas, o ninguna.

Errores y trampas
  • La consigna pide definición y propiedades: si solo se nombran las letras de ACID sin explicarlas, la respuesta queda a medias.
  • Una transacción no es "una operación": es un conjunto de operaciones que se tratan como una.
  • Consistencia no es "que no haya datos repetidos": es que se cumplan todas las reglas de integridad antes y después.
  • En el apunte de Archivos, "archivo de transacciones" es otra cosa: un archivo temporal con los movimientos que después actualizan el archivo maestro. No se mezcla con esta definición.
