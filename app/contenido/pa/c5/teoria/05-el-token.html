Asegurar formularios

5. El token: un código secreto en el formulario y en la sesión

Para qué sirve

Un token es un código al azar que identifica a una entrega del formulario. La idea es guardarlo en dos lados y comparar:

  1. Cuando alguien abre el formulario, PHP inventa un código y lo guarda en $_SESSION['token'].
  2. El mismo código va escondido dentro del formulario, en un campo oculto.
  3. Al enviar, el código viaja con los demás datos y llega en $_POST['token'].
  4. procesoFormulario.php compara los dos. Si coinciden, los datos vienen de ese formulario; si no, se descartan.

El ataque de la sección 4 no pasa: cURL nunca abrió el formulario, así que no conoce el código, y como no trae la cookie de sesión, del lado del servidor $_SESSION['token'] ni siquiera existe.

Lo nuevo de HTML es el campo oculto: <input type="hidden"> es un campo que no se dibuja en la página pero se envía con el formulario como cualquier otro.

Sintaxis

form.php (el formulario) 
<?php
session_start();
$token = rand(5, 1500);
$_SESSION['token'] = $token;
?>
<form action="procesoFormulario.php" method="post">
    <input type="hidden" name="token" value="<?php echo $token ?>">
    <input type="text" name="nombre">
    <input type="text" name="apellido">
    <input type="submit" value="Enviar el formulario">
</form>
procesoFormulario.php (el que recibe) 
<?php
session_start();
if ($_POST['token'] == $_SESSION['token']) {
    // proceso los datos del formulario
} else {
    // descarto todos los datos
}
?>

Por qué == y no ===

Todo lo que llega de un formulario es texto ("629"), pero rand devuelve un entero (629) y así queda en la sesión. == compara el valor y da true; === (Clase 1) exige además el mismo tipo y da false: se probó y con === hasta el envío legítimo se descarta.

El agujero de la comparación del PDF: un envío sin token pasa

Si un programa manda el POST sin el campo token (y sin cookie), $_POST['token'] no existe y $_SESSION['token'] tampoco: los dos valen null (con un Warning cada uno) y null == null da true. Con token= vacío pasa lo mismo, porque "" == null también da true. Se probó: en los dos casos imprimió Proceso los datos del formulario.

La solución es preguntar primero que los dos tengan algo, con empty (sección 3):

if (!empty($_POST['token']) && !empty($_SESSION['token'])
    && $_POST['token'] == $_SESSION['token']) {
    // proceso los datos del formulario
} else {
    // descarto todos los datos
}

Así se probó con los cuatro casos: sin token, token vacío y token equivocado se descartan; solo el envío desde el formulario se procesa. El procesoForm.php de los ejemplos de la cátedra ya pregunta !empty($_POST['token']) antes de comparar.

Erratas del PDF

El PDF escribe $token; = rand(5, 1500);. El ; termina la instrucción después de $token, y el = queda suelto: PHP da Parse error: syntax error, unexpected token "=". Va sin ese punto y coma. También usa comillas tipográficas (type=”hidden”), que van rectas.

Ejemplo 2 — Un token de letras y números (formato del parcial)

El ejemplo formToken.php de la cátedra no usa rand(5, 1500): arma un código de 20 caracteres eligiendo letras y números de una cadena. Para entender cómo, primero una versión sin azar.

Enunciado

¿Cuál es la salida del siguiente script PHP?

<?php
$a = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
$token = "";
for ($i = 0; $i < 3; $i++) {
    $token .= $a[$i * 20];
}
echo strlen($a) . ' ' . $token;
?>

Qué hace cada línea

Dos cosas de la Clase 2 que se usan acá: $a[n] da el carácter de la posición n de una cadena (la primera es la 0), y .= pega un texto al final de una variable. En $a: posiciones 0 a 9 los dígitos, 10 a 35 las minúsculas (a es la 10, k la 20) y 36 a 61 las mayúsculas (A es la 36, E la 40).

Errores y trampas

Lo que el token no resuelve
  • Oculto no quiere decir secreto. El campo hidden está en el HTML: cualquiera lo ve con "Ver código fuente". Lo secreto es que el valor correcto está en la sesión de ese navegador.
  • Un programa que primero abre el formulario lo pasa. La cátedra lo avisa: hay robots (bots) que leen el formulario, token incluido, y lo envían. Se probó: abriendo formToken.php guardando la cookie, copiando el token del HTML y mandándolo por POST, procesoForm.php respondió LOS DATOS PROVIENEN DE NUESTRO FORMULARIO CON TOKEN. Para eso está el captcha (sección 6).
  • El token se puede reusar. Nadie lo borra después de usarlo: el mismo envío repetido se aceptó dos veces seguidas. Recién cambia cuando se vuelve a abrir el formulario.
  • Dos pestañas, un solo token. Cada vez que se abre el formulario se pisa $_SESSION['token']. Si abrís el formulario en dos pestañas, la primera queda con un código viejo y se descarta.
