3. Orden de creación, ALTER y DROP

Primero las tablas a las que se apunta

Un FOREIGN KEY ... REFERENCES Zona(Codigo) solo funciona si la tabla Zona ya existe. Por eso las tablas se crean en orden:

  1. Las que no tienen FK (las "independientes"): Zona, Empleado, Itinerario.
  2. Las que apuntan solo a las del paso 1: Especie (a Zona), Guia y Cuidador (a Empleado).
  3. Al final, las tablas intermedias, que apuntan a dos tablas: Cuidador_Especie, Guia_Itinerario, Itinerario_Zona.

En el parcial, si piden una sola tabla con FK (como Animal), conviene aclarar en una línea que la tabla a la que apunta (Propietario) tiene que estar creada antes.

ALTER TABLE: cambiar una tabla que ya existe

ALTER TABLE Animal ADD Color VARCHAR(20);              -- agrega una columna
ALTER TABLE Animal ALTER COLUMN Raza VARCHAR(80);      -- cambia el tipo de una columna
ALTER TABLE Animal DROP COLUMN Color;                  -- saca una columna
ALTER TABLE Animal ADD CONSTRAINT fk_animal_propietario
  FOREIGN KEY (Documento) REFERENCES Propietario(Documento);  -- agrega una FK

Lo que sigue a -- es un comentario: SQL Server no lo ejecuta. Sirve para anotar qué hace cada línea.

DROP TABLE: borrar una tabla

DROP TABLE Cuidador_Especie;

Borra la tabla entera, con todos sus datos. El orden es el inverso al de creación: no se puede borrar Zona mientras Especie la tenga como FK. En el TP final, los scripts empezaban con DROP TABLE IF EXISTS (borrala solo si existe) para poder correrlos de nuevo desde cero.

Ejemplo 2: ¿ALTER o UPDATE?

(a) A todos los animales se les quiere guardar también el color. (b) Un animal cambió de dueño.

  • (a) cambia la estructura (una columna nueva): ALTER TABLE Animal ADD Color VARCHAR(20); — DDL.
  • (b) cambia un dato de una fila: es un UPDATE (Unidad 4) — DML.
Errores y trampas
  • Crear una tabla con FK antes que la tabla a la que apunta da error: el orden importa.
  • DROP TABLE no pide confirmación ni se deshace (salvo dentro de una transacción con ROLLBACK).
