Los ocho juntos

3. ¿Qué patrón es?

Para qué sirve

La Práctica del parcial son dos preguntas: qué patrones usarías en este enunciado y qué patrón implementa este código, las dos justificando. Esta sección junta los ocho patrones en tablas para decidir rápido y sin mezclarlos.

Paso 1 — De qué habla la necesidad

Los nombres van a estar cambiados

La cátedra reemplaza los nombres originales para que no delaten al patrón: Facade fue Pantalla; Adapter fue conversor; Singleton, Inicio_Serie; Observer, alarma; Strategy, dispositivo; Composite, molecula. Los que suelen quedar son los nombres de los métodos (GetInstance, Attach, Notify, Update, SpecificRequest, Operation1) y los textos entre comillas ("initializes subsystems", "Adaptee"). Sirven de confirmación, pero la respuesta se justifica con la forma.

Los que más se confunden

ParLa pregunta que los separa
Factory Method / Abstract Factory¿Se crea un tipo de cosa (FM) o varias que combinan (AF)?
Adapter / Facade¿Se envuelve una clase para darle una interfaz que ya existía (Adapter) o varias para dar una interfaz nueva y simple (Facade)?
Composite / ObserverLos dos tienen lista y bucle. ¿La lista es del mismo tipo que la clase que la tiene y el resultado vuelve (Composite), o es de otra interfaz y solo se avisa (Observer)?
Strategy / Observer¿Guarda una y la puede cambiar (Strategy) o guarda muchas y les avisa (Observer)?
Strategy / Factory Method¿Las variantes son formas de hacer una tarea (Strategy) o de crear un objeto (Factory Method)?
Singleton / FacadeNo se excluyen: Singleton dice cuántos objetos hay; Facade, qué hace esa clase. Una fachada puede ser Singleton.

Ejemplo 1 — Con formato de parcial: un enunciado con tres patrones

Inventado · con la forma del Parcial 2025, Práctica 1

"A partir del siguiente enunciado identifique cuáles serían los patrones de diseño que utilizaría y justifique por qué eligió los mismos."

"La empresa Bicis a Medida S.R.L. fabrica y vende bicicletas personalizadas a través de su sitio web. Los clientes recorren el catálogo y arman su bicicleta eligiendo el cuadro, el rodado, la transmisión y los accesorios. Según esas elecciones, el sistema debe aplicar el criterio de armado y de presupuesto que resulte más conveniente, y la empresa quiere poder incorporar nuevos criterios sin modificar el módulo de ventas."

"Una vez confirmada la compra, el pedido pasa al taller. Para cada tipo de bicicleta (de ruta, de montaña, urbana o plegable) existe un procedimiento de armado específico que construye la unidad correspondiente, sin que el área de ventas tenga que conocer los detalles del taller. Se busca que la creación de las bicicletas sea flexible, de manera que puedan agregarse nuevos tipos sin afectar la lógica de compra."

"Cuando la bicicleta está terminada, el sistema avisa automáticamente al cliente por correo electrónico o por mensaje en el sitio. Además, el cliente puede suscribirse para recibir las novedades de su pedido, de modo que cualquier cambio (demoras, avances del armado, despacho) se le comunique en el momento."

El método: un párrafo, una necesidad, un patrón.

PárrafoLa necesidadLa frase que lo delataPatrón
1. La compraHay varias formas de armar y presupuestar, y se elige una según lo que pide el cliente"el sistema debe aplicar el criterio de armado y de presupuesto que resulte más conveniente"Strategy (de comportamiento)
2. El tallerCrear distintos tipos de bicicleta sin que ventas conozca los detalles, y poder agregar tipos"para cada tipo de bicicleta (...) existe un procedimiento de armado específico que construye la unidad correspondiente"Factory Method (creacional)
3. Los avisosCuando el pedido cambia, el cliente se entera solo"el cliente puede suscribirse (...) cualquier cambio se le comunique en el momento"Observer (de comportamiento)
Cómo quedaría escrita la respuesta

Strategy, para el armado y el presupuesto. Se usa cuando hay varias formas de hacer una misma tarea y se quiere poder cambiar de una a otra mientras el programa corre, y eso pide el enunciado: el sistema "debe aplicar el criterio de armado y de presupuesto que resulte más conveniente", según lo que eligió el cliente. Cada forma (cada criterio de armado y presupuesto) va en su propia clase, todas con la misma interfaz, y el módulo de ventas, que es el contexto, guarda una y le delega la tarea. Así se agregan formas nuevas sin modificar el módulo de ventas.

Factory Method, para el taller. Se usa cuando una clase no puede saber de antemano qué tipo exacto de objeto tiene que crear: acá, el área de ventas no sabe qué bicicleta le toca (de ruta, de montaña, urbana o plegable). El enunciado lo dice: "existe un procedimiento de armado específico que construye la unidad correspondiente". La creación se saca a un método, el método fábrica, que una clase base declara y cada subclase sobrescribe para devolver su bicicleta: hay un creador por cada tipo. Así se agregan tipos nuevos sin modificar el código que los usa, "sin afectar la lógica de compra".

Observer, para los avisos. Se usa cuando un cambio en un objeto se tiene que avisar a otros, y no se sabe de antemano cuántos ni cuáles son; el enunciado lo dice: el cliente "puede suscribirse para recibir las novedades de su pedido", y cualquier cambio se le comunica "en el momento". El pedido es el notificador: guarda una lista de suscriptores (los clientes) y les avisa a todos; cada uno se puede suscribir o dar de baja cuando quiera. Así otro medio de aviso u otro interesado se suma como un suscriptor más, sin modificar el pedido.

Las dos trampas de este enunciado
  • "Fabrica", "taller" y "armado" tientan a Abstract Factory. Pero acá no hay familias que deban combinar: hay tipos de bicicleta, cada uno con su procedimiento. Es Factory Method.
  • "Arman su bicicleta eligiendo..." podría sonar a creación, pero la frase que decide en el primer párrafo es "el criterio (...) más conveniente": se elige cómo armar y presupuestar.

Tiene los mismos tres patrones, y en el mismo orden, que el enunciado de la Práctica 1 del parcial 2025 (Muebles Express), que está resuelto en Evaluación.

Ejemplo 2 — Reconocer un código en cuatro preguntas

El orden importa: cada pregunta descarta patrones.

  1. ¿Hay algo static y un constructor que no es público?
    Sí → Singleton. No → sigo.
  2. ¿Alguna clase hereda de otra?
    Ninguna → Facade. Alguna → sigo.
  3. ¿Hay métodos cuyo trabajo es devolver un new de otra clase?
    Sí, uno → Factory Method. Sí, varios que devuelven cosas de distinto tipo → Abstract Factory. No → sigo.
  4. La clase que guarda a otras, ¿qué guarda?
    • Un objeto de una clase suelta, de nombre "raro" → Adapter.
    • Una lista de su propio tipo → Composite.
    • Una lista de otra interfaz, con métodos para agregar, quitar y avisar → Observer.
    • Un solo objeto de una interfaz, que se puede cambiar → Strategy.

Probándolo con este código (se muestran solo las declaraciones):

class Horno {
 public:
  std::string Operation1() const;
  std::string OperationN() const;
};

class Empaque {
 public:
  std::string Operation1() const;
  std::string OperationZ() const;
};

class Panaderia {
 protected:
  Horno* horno_;
  Empaque* empaque_;

 public:
  Panaderia(Horno* horno, Empaque* empaque);
  std::string Operation();
};
PreguntaRespuestaResultado
1. ¿static y constructor no público?No hay ningún static; el constructor de Panaderia es públicoNo es Singleton
2. ¿Alguna clase hereda de otra?Ninguna tiene : public ...Facade

Dos preguntas. Después se confirma con el resto: Panaderia guarda un puntero a cada una de las otras dos y Operation() las llama en orden.

Errores y trampas

La respuesta tiene tres partes

Qué patrón, qué lo delata (la frase del enunciado o los elementos del código) y qué resuelve ahí. Las consignas dicen "justifique" y "explique qué elementos ayudaron a identificarlo": nombrar el patrón solo es media respuesta.

No forzar un patrón por párrafo

El método "un párrafo, una necesidad" sirve para buscar, no es una regla: puede haber un párrafo de contexto sin ningún patrón, o dos necesidades en el mismo. Lo que manda es que cada patrón tenga su frase.
