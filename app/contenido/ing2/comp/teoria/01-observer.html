Comportamiento

1. Observer

También llamado Observador, Publicación-Suscripción, Event-Subscriber o Listener.

Para qué sirve

El problema, con el ejemplo del apunte: un cliente espera que llegue un producto a una tienda.

  • Si el cliente va todos los días a preguntar, pierde el tiempo: casi todos los viajes son en vano.
  • Si la tienda les manda un mail a todos cada vez que llega algo, molesta a los que no les interesa.

La salida es una lista de suscripción: el que quiere enterarse se anota, la tienda les avisa solo a los anotados, y el que ya no quiere se borra.

En el patrón, los dos papeles tienen nombre:

  • el notificador (también sujeto o publicador; en los códigos, Subject): el objeto al que le pasan cosas interesantes;
  • los suscriptores (también observadores; en los códigos, Observer): los objetos que quieren enterarse.

Analogía del apunte: la suscripción a una revista. No se va al kiosco a ver si salió el número nuevo: la editorial tiene la lista de suscriptores y se lo manda a cada uno, y cualquiera puede darse de baja cuando quiera.

Propósito

Observer es un patrón de comportamiento que permite definir un mecanismo de suscripción para notificar a varios objetos sobre cualquier evento que le suceda al objeto que están observando.

La idea de la solución

El mecanismo de suscripción son dos cosas dentro del notificador:

  1. una lista donde guarda a los suscriptores;
  2. métodos públicos para agregar y quitar suscriptores de esa lista, más uno que recorre la lista avisándole a cada uno.

Para que el notificador pueda avisarles a objetos de clases muy distintas sin conocerlas, todos los suscriptores cumplen una misma interfaz, con un solo método: el que el notificador llama para avisar.

Estructura

ParteQué esEn el ejemplo de la tienda
Notificador (Publisher / Subject)El objeto observado. Guarda la lista de suscriptores y tiene los métodos para suscribir, desuscribir y notificar. Cuando le pasa algo, llama a notificar().Tienda
Suscriptor (Subscriber / Observer)La interfaz de los que quieren enterarse. Tiene un método, actualizar() (en los códigos, Update).Suscriptor
Suscriptores ConcretosCada clase que reacciona al aviso, a su manera.Cliente

Cómo dibujarlo de memoria:

  • A la izquierda el Notificador, con la lista y sus tres métodos: suscribir, desuscribir, notificar.
  • Un rombo vacío del Notificador a la interfaz Suscriptor, con un *: tiene muchos.
  • Debajo de la interfaz, los suscriptores concretos, con línea punteada.

En los códigos de la cátedra el notificador también tiene su interfaz (ISubject), con la clase concreta debajo. Es opcional: el patrón es el mismo.

Ejemplo 1 — En C++: la tienda avisa cuando llega un producto

El programa, en 6 partes. Los números de la izquierda son los renglones del programa completo; los renglones resaltados son los que hay que mirar.

2Lo que tiene que tener quien quiera enterarseSuscriptor

class Suscriptor {
 public:
  virtual ~Suscriptor() {}
  virtual void actualizar(std::string novedad) = 0;
};

Un solo método: actualizar().

3La lista y cómo anotarseNotificador

class Tienda {
 private:
  std::list<Suscriptor*> suscriptores_;

 public:
  void suscribir(Suscriptor* s) {
    suscriptores_.push_back(s);
  }

  void desuscribir(Suscriptor* s) {
    suscriptores_.remove(s);
  }

La lista es de punteros a la interfaz: la tienda no sabe qué clase es cada anotado.

4AvisarNotificador

  void notificar(std::string novedad) {
    for (Suscriptor* s : suscriptores_) {
      s->actualizar(novedad);
    }
  }

  void recibirProducto(std::string producto) {
    std::cout << "Tienda: llego " << producto << "\n";
    notificar(producto);
  }
};

El corazón del patrón: recorre la lista y le llama actualizar() a cada uno. recibirProducto() es el trabajo normal de la tienda, que al final avisa.

5Uno que se enteraSuscriptor concreto

class Cliente : public Suscriptor {
 private:
  std::string nombre_;

 public:
  Cliente(std::string nombre) : nombre_(nombre) {}

  void actualizar(std::string novedad) override {
    std::cout << nombre_ << " se entero de que llego " << novedad << "\n";
  }
};

Dice qué hace cuando le avisan.

6El programa

int main() {
  Tienda tienda;
  Cliente* ana = new Cliente("Ana");
  Cliente* luis = new Cliente("Luis");

  tienda.suscribir(ana);
  tienda.suscribir(luis);
  tienda.recibirProducto("el celular nuevo");

  tienda.desuscribir(luis);
  tienda.recibirProducto("la tablet nueva");

  delete ana;
  delete luis;
  return 0;
}

Dos clientes se anotan, llega un producto, uno se borra, llega otro producto.

Cómo reconocerlo

DóndeQué lo delata
En un enunciadoUn hecho que dispara avisos automáticos a otros: "cada vez que se registre el acceso de un usuario, la clase Logger debe escribir en un archivo el suceso", "cada vez que se realice un movimiento, se envíe una alerta al administrador y se registre este suceso en una tabla de auditoría", "cuando se modifique el contenido del archivo, automáticamente se invoquen a los 3 exportadores", "cada vez que se cree una notificación, se envíe un mail al administrador". Y si agrega "es deseable a futuro implementar nuevos mecanismos de alerta", lo confirma: son suscriptores nuevos.
En un código
  1. una clase con una lista de punteros a una interfaz (std::list<IObserver*>);
  2. tres métodos en esa clase: Attach, Detach y Notify (agregar, quitar, avisar);
  3. Notify es un bucle que llama al mismo método en cada elemento de la lista: Update;
  4. la interfaz de la lista tiene un solo método, Update, y las clases que la cumplen se anotan solas en el notificador (subject_.Attach(this)).

Ventajas y desventajas

VentajasDesventajas
  • Principio de abierto/cerrado: se agregan clases suscriptoras nuevas sin cambiar el código del notificador (y al revés, si el notificador tiene interfaz).
  • Se pueden establecer relaciones entre objetos durante la ejecución: suscribirse y desuscribirse mientras el programa corre.
  • Los suscriptores son notificados en un orden aleatorio: no se puede contar con que uno se entere antes que otro.

Dónde se usa

  • Cuando los cambios en un objeto pueden requerir cambiar otros, y no se sabe de antemano cuáles ni cuántos, o cambian mientras el programa corre.
  • Interfaces gráficas (el ejemplo del apunte): un botón avisa a todo el código que se "colgó" de él cuando el usuario hace clic.
  • Alertas y auditoría: cuando pasa algo, mandar un mail y dejar asentado el suceso en un registro.
  • Notificaciones a usuarios suscriptos: el estado de un pedido, una novedad de la tienda.

Inventado · con la forma del Parcial 2024, ejercicio 2

"Realice el diagrama (mediante UML) del patrón Observer, dé una breve descripción de su usabilidad y mencione 2 ejemplos."

La consigna pide tres cosas; la respuesta tiene que tener las tres:

  2. La descripción: "Observer es un patrón de comportamiento que se usa cuando un cambio en un objeto se tiene que avisar a otros, y no se sabe de antemano cuántos ni cuáles son.   3. Dos ejemplos: no alcanza con nombrarlos. A cada uno se le suma una línea que diga por qué ahí va el patrón:

Ejemplo 4 — Con formato de parcial: identificar los patrones de un enunciado

Inventado · con la forma del Parcial 2025, Práctica 1

"A partir del siguiente enunciado identifique cuáles serían los patrones de diseño que utilizaría y justifique por qué eligió los mismos."

"FitLife es una cadena de gimnasios que está desarrollando su aplicación para socios. El valor de la cuota se calcula de diferentes formas según el plan contratado (mensual, por clase o familiar). El socio puede cambiar de plan en cualquier momento, y la cadena quiere poder agregar planes nuevos sin modificar el módulo de cobros."

"Las clases grupales tienen cupo limitado. Cada vez que se libera un lugar en una clase que estaba completa, la aplicación debe avisar automáticamente a todos los socios anotados en la lista de espera de esa clase. Los socios pueden anotarse o darse de baja de la lista cuando quieran, y se prevé avisar también al profesor."

"Para inscribir a un socio nuevo, el personal de recepción hoy tiene que operar con tres módulos distintos: el de fichas médicas, el de cobros y el de credenciales, respetando ese orden. Se pide que recepción cuente con una única operación, simple, que realice la inscripción completa sin necesidad de conocer cada módulo."

El enunciado mezcla Observer con otros dos patrones, como en el parcial. El método: un párrafo, una necesidad, un patrón. En cada párrafo se busca qué se necesita y la frase que lo dice.

PárrafoLa necesidadLa frase que lo delataPatrón
1. La cuotaVarias formas de calcular la cuota, que se pueden cambiar"se calcula de diferentes formas según el plan (...) puede cambiar de plan en cualquier momento"Strategy (de comportamiento)
2. La lista de esperaQue los socios se enteren solos cuando se libera un lugar"Cada vez que se libera un lugar (...) avisar automáticamente a todos (...) anotarse o darse de baja"Observer (de comportamiento)
3. La inscripciónHacer con una sola operación lo que hoy son tres módulos en orden"operar con tres módulos distintos (...) una única operación, simple"Facade (estructural)
Cómo quedaría escrita la respuesta

Strategy, para el valor de la cuota. La cuota "se calcula de diferentes formas según el plan" y el socio "puede cambiar de plan en cualquier momento". Cada forma de calcular es una estrategia con la misma interfaz, y el socio (el contexto) guarda la de su plan y le delega el cálculo. Un plan nuevo es una clase más, sin modificar el módulo de cobros.

Observer, para la lista de espera. "Cada vez que se libera un lugar" hay que "avisar automáticamente a todos los socios anotados", que pueden "anotarse o darse de baja" cuando quieran. La clase grupal es el notificador, con su lista de espera, y los socios son los suscriptores. Avisar también al profesor es agregar otro suscriptor, sin modificar la clase.

Facade, para la inscripción. Hoy recepción debe "operar con tres módulos distintos" en orden, y se pide "una única operación, simple". Una fachada guarda los tres módulos y ofrece esa operación, que carga la ficha médica, registra el cobro y emite la credencial. Recepción no necesita conocer ningún módulo.

Cada justificación tiene las mismas tres partes: el patrón y para qué parte del sistema, la frase del enunciado que lo pide (entre comillas) y cómo queda armado, con lo que se gana.

Las trampas de este enunciado
  • Los párrafos 1 y 2 son los dos de comportamiento. En el 1 el socio tiene un plan y lo puede cambiar: Strategy. En el 2 la clase tiene muchos anotados y les avisa a todos: Observer.
  • "Cambiar de plan" no es crear nada: el socio sigue siendo el mismo objeto y lo que cambia es cómo se le calcula la cuota.

Ejemplo 5 — Con formato de parcial: reconocerlo en un código

Inventado · con la forma de la Guía N°1, ejercicio 2

"Dado el siguiente código identifique qué tipo de patrón se implementa. Justifique."

Los renglones resaltados son los que lo delatan:

#include <iostream>
#include <list>
#include <string>

class IVisor {
 public:
  virtual ~IVisor() {}
  virtual void Update(const std::string& mensaje) = 0;
};

class Estacion {
 private:
  std::list<IVisor*> list_visor_;
  std::string mensaje_;

 public:
  void Attach(IVisor* visor) {
    list_visor_.push_back(visor);
  }
  void Detach(IVisor* visor) {
    list_visor_.remove(visor);
  }
  void Notify() {
    for (IVisor* visor : list_visor_) {
      visor->Update(mensaje_);
    }
  }
  void CreateMessage(const std::string& mensaje) {
    this->mensaje_ = mensaje;
    Notify();
  }
};

class Visor : public IVisor {
 private:
  std::string nombre_;

 public:
  Visor(const std::string& nombre) : nombre_(nombre) {}
  void Update(const std::string& mensaje) override {
    std::cout << nombre_ << ": nuevo dato -> " << mensaje << "\n";
  }
};

int main() {
  Estacion estacion;
  Visor visor1("Visor 1");
  Visor visor2("Visor 2");
  estacion.Attach(&visor1);
  estacion.Attach(&visor2);
  estacion.CreateMessage("22 grados");
  estacion.Detach(&visor1);
  estacion.CreateMessage("25 grados");
  return 0;
}
Visor 1: nuevo dato -> 22 grados
Visor 2: nuevo dato -> 22 grados
Visor 2: nuevo dato -> 25 grados
RenglónLo que se veQué parte del patrón es
5Una interfaz con un solo método virtual puro, Update().El Suscriptor (Observer)
13Una lista de punteros a esa interfaz, que es otra clase.La lista de suscriptores, en el Notificador (Estacion)
17Attach suma a la lista y Detach saca.Suscribir y desuscribir
23Recorre la lista y llama al mismo método de cada uno. No vuelve ningún resultado.Notificar
34La clase que escribe qué hace cuando le avisan.El Suscriptor Concreto
52Uno se da de baja mientras el programa corre: el segundo dato ya no le llega.La suscripción cambia en tiempo de ejecución

Respuesta: "Es el patrón Observer (de comportamiento). Estacion es el notificador: guarda una lista de IVisor* y tiene Attach(), Detach() y Notify(). IVisor es la interfaz suscriptor, con Update(), y Visor es el suscriptor concreto. Cuando la estación recibe un dato nuevo (CreateMessage()) llama a Notify(), que avisa a todos los que estén suscritos en ese momento: por eso el segundo dato le llega solo al Visor 2."

Los tres verbos que lo delatan

Attach, Detach y Notify en una clase, y Update en una interfaz. Son los nombres del ejemplo de Refactoring.Guru, y en castellano suelen quedar como suscribir, desuscribir, notificar y actualizar.

Ejemplo 6 — Con formato de parcial: agregarlo a un diagrama

Guía N°1 · ejercicio 1 (segundo pedido)

"Considere el siguiente diagrama de UML, el cual modela un módulo de seguridad de una aplicación. Dada esta implementación se necesita: cada vez que se registre el acceso de un usuario, la clase Logger debe escribir en un archivo el suceso, con el fin de registrar dicha información."

"Indicar qué patrón se puede utilizar y justificar su uso. Reescribir el diagrama de UML con la solución implementada."

Qué hay en el diagrama. ControladorSeguridad es el que registra los accesos (registrarAcceso()) y Logger el que sabe escribir (escribirLog()). Hoy están unidos por una línea simple: el controlador conoce directamente al logger y tendría que llamarlo él. El ejercicio tiene un primer pedido, sobre ControladorSeguridad: es Singleton y está resuelto en la Unidad 4A, sección 1.

Qué se cambia, en orden:

  1. Crear la interfaz Suscriptor. Observador, con un solo método: actualizar(acceso).
  2. Convertir a la clase que cambia en Notificador. En ControladorSeguridad se agregan la lista - observadores: Observador[] y los métodos suscribir(o), desuscribir(o) y notificar(). registrarAcceso() queda, y ahora termina llamando a notificar().
  3. Convertir al Logger en Suscriptor Concreto. Logger cumple Observador (línea punteada con triángulo) y gana actualizar(acceso), que por dentro llama al escribirLog() que ya tenía.
  4. Cambiar la línea entre las dos clases. Se borra la línea directa de ControladorSeguridad a Logger y se dibuja el rombo de ControladorSeguridad a la interfaz Observador, con *.

El diagrama modificado:

Justificación: "Se utiliza Observer porque cada vez que se registra el acceso de un usuario otra clase tiene que reaccionar, sola. ControladorSeguridad es el notificador: guarda una lista de observadores y, al registrar un acceso, los notifica. Logger es un suscriptor: implementa Observador y en actualizar() escribe el suceso en el archivo. El controlador ya no depende del logger, y otro mecanismo de registro se suma como un suscriptor más."

A tener en cuenta al modificar el diagrama
  • Aunque hoy haya un solo suscriptor (el Logger), la lista y la interfaz van igual: son las que permiten sumar otros sin tocar el controlador.
  • El rombo va a la interfaz Observador, no al Logger.
  • No se borra nada de lo que estaba: escribirLog() y registrarAcceso() siguen en su clase.
  • La consigna dice "patrón / patrones": con el Singleton del primer pedido, ControladorSeguridad termina con las dos cosas (el atributo estático, el constructor privado y obtenerInstancia(), además de lo de Observer). En la hoja van sobre el mismo diagrama.

Errores y trampas

Quién llama a quién

El suscriptor no pregunta: es el notificador el que lo llama. Si en la solución una clase "consulta cada tanto si hubo cambios", no es Observer; es el problema que Observer viene a resolver.

La lista es de la interfaz, no de una clase concreta

Si ControladorSeguridad guardara directamente "un Logger", funcionaría para ese caso pero no habría patrón: no se podría sumar otro tipo de observador sin modificarlo.

Con qué se confunde

Con Composite, porque los dos tienen una clase con una lista y un bucle que llama al mismo método en cada elemento. En Composite la lista es del mismo tipo que la clase que la tiene (por eso hay árbol) y el resultado vuelve (se suma, se junta). En Observer la lista es de otra interfaz, y solo se avisa: no se espera respuesta.
