3. Facade

También llamado Fachada.

Para qué sirve

Para hacer algo que desde afuera parece simple ("comprar un producto", "convertir un video"), muchas veces el código tiene que manejar un montón de clases: crearlas a todas, saber cuál depende de cuál y llamar a sus métodos en el orden correcto. A ese conjunto de clases que trabajan juntas se le dice subsistema.

  • Si cada parte del programa habla directo con todas esas clases, queda acoplada a sus detalles.
  • Y los mismos cuatro o cinco pasos quedan repetidos en todos lados.

Una fachada es una clase que conoce el subsistema y ofrece unos pocos métodos simples. El resto del programa habla solo con ella, y ella reparte el trabajo. Puede ofrecer menos funciones que usar el subsistema directo, pero ofrece las que hacen falta.

Analogía del apunte: pedir por teléfono a una tienda. El operador que atiende es la fachada: uno le dice qué quiere y él se ocupa del sistema de pedidos, del pago y del envío.

Propósito

Facade es un patrón estructural que proporciona una interfaz simplificada a una biblioteca, un framework o cualquier otro grupo complejo de clases.

Estructura

ParteQué esEn el ejemplo de la tienda
Fachada (Facade)La clase que da acceso simple al subsistema. Guarda (o crea) los objetos del subsistema y sabe a quién pedirle cada cosa y en qué orden.Tienda, con comprar()
Subsistema ComplejoLas clases que hacen el trabajo real. No saben que la fachada existe: no tienen ninguna referencia a ella.Inventario, Pagos, Envios
ClienteUsa la fachada en vez de llamar directo a las clases del subsistema.main

Cómo dibujarlo de memoria: un abanico.

  • El Cliente apunta a la Fachada, y de la Fachada salen flechas a cada clase del subsistema.
  • No hay ninguna interfaz ni herencia. Es el único de los ocho patrones cuyo diagrama no tiene triángulos: las clases del subsistema no tienen nada en común entre sí.
  • Las flechas van solo de la fachada hacia el subsistema, nunca al revés.

Ejemplo 1 — En C++: comprar en una tienda en línea

Para concretar una compra hay que consultar el inventario, cobrar y despachar. Tres subsistemas, un solo método para el que compra.

El programa, en 5 partes. Los números de la izquierda son los renglones del programa completo; los renglones resaltados son los que hay que mirar.

1Las bibliotecas

#include <iostream>
#include <string>

2Las clases que hacen el trabajoSubsistema

class Inventario {
 public:
  bool hayStock(std::string producto) const {
    std::cout << "Inventario: hay stock de " << producto << "\n";
    return true;
  }
};

class Pagos {
 public:
  void cobrar(double monto) const {
    std::cout << "Pagos: se cobraron " << monto << " pesos\n";
  }
};

class Envios {
 public:
  void despachar(std::string producto) const {
    std::cout << "Envios: se despacho " << producto << "\n";
  }
};

Tres clases sueltas: no heredan de nada ni se conocen entre sí.

3La clase que las juntaFachada

class Tienda {
 private:
  Inventario* inventario_;
  Pagos* pagos_;
  Envios* envios_;

 public:
  Tienda() {
    inventario_ = new Inventario;
    pagos_ = new Pagos;
    envios_ = new Envios;
  }

  ~Tienda() {
    delete inventario_;
    delete pagos_;
    delete envios_;
  }

Un puntero a cada clase del subsistema, creados en el constructor. El cliente no se entera de que existen.

4El método simpleFachada

  void comprar(std::string producto, double monto) {
    if (inventario_->hayStock(producto)) {
      pagos_->cobrar(monto);
      envios_->despachar(producto);
    }
  }
};

Adentro llama a los tres subsistemas en el orden correcto. Ese orden está escrito una sola vez, acá.

5El que la usaCliente

int main() {
  Tienda tienda;
  tienda.comprar("teclado", 15000);
  return 0;
}

Crea solo la fachada y hace una sola llamada.

Cómo reconocerlo

DóndeQué lo delata
En un enunciado"una interface fácil y de simple acceso para que una clase Cliente pueda interactuar de forma fácil", "una fachada para simplificar la interacción del cliente con estos subsistemas", "múltiples subsistemas", "una interfaz única que permita realizar operaciones comunes".
En un código
  1. varias clases sueltas, sin clase base común ni virtual, cada una con sus métodos (Subsystem1, Subsystem2...);
  2. una clase que guarda un puntero a cada una de ellas (y muchas veces las crea en su constructor);
  3. esa clase tiene uno o pocos métodos que por dentro llaman en secuencia a los métodos de las otras;
  4. el código cliente usa solo esa clase.
La pista más rápida: no hay herencia entre las clases del patrón.

Ventajas y desventajas

VentajasDesventajas
  • Se aísla el código de la complejidad de un subsistema.
  • Una fachada puede convertirse en un objeto todopoderoso, acoplado a todas las clases de la aplicación.

Dónde se usa

  • Cuando se necesita una interfaz limitada pero directa a un subsistema complejo: el ejemplo del apunte es una aplicación que solo quiere codificar(archivo, formato) de una biblioteca profesional de conversión de video.
  • Para estructurar un subsistema en capas: cada capa se comunica con la de abajo solo por su fachada.
  • En una tienda en línea: inventario, pedidos y envíos detrás de una sola clase.

Según el apunte, una fachada muchas veces se puede hacer Singleton, porque con un único objeto fachada alcanza.

Ejemplo 2 — Con formato de parcial: dibujarlo y explicarlo

Inventado · con la forma del Parcial 2024, ejercicio 2

"Realice el diagrama (mediante UML) del patrón Facade, dé una breve descripción de su usabilidad y mencione 2 ejemplos."

La consigna pide tres cosas; la respuesta tiene que tener las tres:

  1. El diagrama: el Cliente; la Fachada en el medio, con un atributo por cada clase del subsistema y un método simple; y a la derecha las clases del subsistema, sin ninguna flecha de vuelta hacia la fachada.
  2. La descripción: "Facade es un patrón estructural que se usa cuando para hacer una tarea hay que coordinar varias clases de un subsistema complicado. Una clase nueva, la fachada, ofrece una interfaz simple con las operaciones que el cliente necesita y por dentro llama a las clases del subsistema en el orden correcto."
  3. Dos ejemplos: no alcanza con nombrarlos. A cada uno se le suma una línea que diga por qué ahí va el patrón:
    • Un conversor de video. "Convertir un video obliga a usar varias clases de una librería (códecs, mezclador de audio, compresor) en un orden preciso. La fachada ConversorDeVideo ofrece un solo método, convertir(), y hace todo eso por dentro."
    • La compra en una tienda en línea. "Comprar implica verificar el stock, cobrar y despachar. La fachada Tienda tiene comprar(), que llama a Inventario, Pagos y Envios en orden; la pantalla de compra no conoce a ninguna de las tres."

Ejemplo 3 — Con formato de parcial: aplicarlo a un enunciado

Inventado · parecido a la Práctica 03, ejercicio 2

"En un centro médico, para dar un turno hay que usar tres clases: AgendaMedica (para saber si el médico tiene lugar), ObraSocial (para validar la cobertura del paciente) y Notificaciones (para enviar la confirmación), siempre en ese orden. Se necesita una interfaz fácil y de simple acceso para que la clase Recepcion pueda dar un turno sin conocer esos subsistemas. Indique qué patrón de diseño aplicaría, justifique y realice el diagrama UML."

Frase del enunciadoQué significaParte del patrón
"hay que usar tres clases (...) siempre en ese orden"Un subsistema de varias clases que hay que coordinarLas clases del subsistema
"una interfaz fácil y de simple acceso"La frase que pide Facade: un solo punto de entradaLa Fachada: GestorDeTurnos, con el método darTurno()
"para que la clase Recepcion pueda dar un turno"Quién va a usar esa interfazEl Cliente
"sin conocer esos subsistemas"El cliente no puede tener flechas hacia las tres clasesEl cliente apunta solo a la fachada

Justificación, en tres partes: qué patrón y qué frase lo pide, cómo queda armado en este caso y qué se gana.

  1. Qué patrón y por qué: "Se aplica Facade, un patrón estructural, porque dar un turno obliga a coordinar tres clases en un orden fijo y el enunciado pide una interfaz fácil y de simple acceso."
  2. Cómo se aplica: "AgendaMedica, ObraSocial y Notificaciones son las clases del subsistema, y no cambian. Se agrega GestorDeTurnos, la fachada: guarda un objeto de cada una y ofrece darTurno(paciente, medico), que verifica la agenda, valida la cobertura y envía la confirmación. Recepcion, el cliente, solo conoce a la fachada."
  3. Qué se gana: "La recepción da un turno con una sola llamada y no depende del subsistema: si cambia la forma de validar la obra social, se modifica la fachada y no la recepción."

Ejemplo 4 — Con formato de parcial: identificar los patrones de un enunciado

Inventado · con la forma del Parcial 2025, Práctica 1

"A partir del siguiente enunciado identifique cuáles serían los patrones de diseño que utilizaría y justifique por qué eligió los mismos."

"ViajaFácil es una agencia de viajes en línea. Para concretar una reserva, el sistema debe interactuar con varios subsistemas (el de vuelos, el de hoteles y el de pagos), cada uno con sus propias operaciones y en una secuencia determinada. Se pretende que el sitio web disponga de un acceso simple y unificado para reservar un viaje completo, sin tener que conocer el funcionamiento de cada subsistema."

"La agencia ofrece sus paquetes en dos categorías, Económica y Premium. Cada categoría incluye su propio tipo de vuelo, de alojamiento y de traslado, y los servicios de una categoría no deben combinarse con los de la otra. El sistema debe armar el paquete completo según la categoría elegida, y se prevé incorporar una categoría Corporativa."

"Por último, el precio final de cada paquete se calcula aplicando una política de descuento, que puede ser por temporada baja, por compra anticipada o por cliente frecuente. La política se elige al momento de la compra y debe poder cambiarse sin modificar el cálculo del resto del paquete."

El enunciado mezcla Facade con otros dos patrones, como en el parcial. El método: un párrafo, una necesidad, un patrón. En cada párrafo se busca qué se necesita y la frase que lo dice.

PárrafoLa necesidadLa frase que lo delataPatrón
1. La reservaHacer con una sola operación lo que exige coordinar tres subsistemas"interactuar con varios subsistemas (...) un acceso simple y unificado"Facade (estructural)
2. Las categoríasCrear servicios que tienen que combinar entre sí, y poder sumar categorías"Cada categoría incluye su propio tipo de vuelo, de alojamiento y de traslado (...) no deben combinarse con los de la otra"Abstract Factory (creacional)
3. El descuentoVarias formas de calcular el descuento, que se eligen al comprar"una política de descuento (...) se elige al momento de la compra y debe poder cambiarse"Strategy (de comportamiento)
Cómo quedaría escrita la respuesta

Facade, para la reserva. Reservar obliga a "interactuar con varios subsistemas" (vuelos, hoteles y pagos) "en una secuencia determinada", y se pide "un acceso simple y unificado". Una fachada guarda los tres subsistemas y ofrece una operación para reservar el viaje completo. El sitio web depende solo de la fachada.

Abstract Factory, para armar los paquetes. "Cada categoría incluye su propio tipo de vuelo, de alojamiento y de traslado" y los de una categoría "no deben combinarse con los de la otra": son familias de productos. Una fábrica abstracta tiene un método de creación por cada servicio y hay una fábrica concreta por categoría (Económica, Premium). La categoría Corporativa se suma con otra fábrica.

Strategy, para el descuento. El precio se calcula "aplicando una política de descuento" que "se elige al momento de la compra" y "debe poder cambiarse". Cada política (temporada baja, compra anticipada, cliente frecuente) es una estrategia, y el paquete, que es el contexto, le delega el cálculo del descuento.

Cada justificación tiene las mismas tres partes: el patrón y para qué parte del sistema, la frase del enunciado que lo pide (entre comillas) y cómo queda armado, con lo que se gana.

Las trampas de este enunciado
  • Los párrafos 1 y 2 hablan los dos de vuelos y hoteles, pero piden cosas distintas: el 1, simplificar el uso de lo que ya existe (Facade); el 2, crear servicios que combinen (Abstract Factory).
  • "Política de descuento" es otra forma de decir estrategia: una manera de hacer un cálculo, que se puede cambiar.

Ejemplo 5 — Con formato de parcial: reconocerlo en un código

Inventado · con la forma de la Guía N°1, ejercicio 2

"Dado el siguiente código identifique qué tipo de patrón se implementa. Justifique."

Los renglones resaltados son los que lo delatan:

#include <iostream>
#include <string>

class Horno {
 public:
  std::string Operation1() const {
    return "Horno: listo!\n";
  }
  std::string OperationN() const {
    return "Horno: a cocinar!\n";
  }
};

class Empaque {
 public:
  std::string Operation1() const {
    return "Empaque: preparado!\n";
  }
  std::string OperationZ() const {
    return "Empaque: a embolsar!\n";
  }
};

class Panaderia {
 protected:
  Horno* horno_;
  Empaque* empaque_;

 public:
  Panaderia(Horno* horno = nullptr, Empaque* empaque = nullptr) {
    this->horno_ = horno ? horno : new Horno;
    this->empaque_ = empaque ? empaque : new Empaque;
  }
  ~Panaderia() {
    delete horno_;
    delete empaque_;
  }
  std::string Operation() {
    std::string result = "Panaderia inicia los subsistemas:\n";
    result += this->horno_->Operation1();
    result += this->empaque_->Operation1();
    result += "Panaderia les ordena trabajar:\n";
    result += this->horno_->OperationN();
    result += this->empaque_->OperationZ();
    return result;
  }
};

void ClientCode(Panaderia* panaderia) {
  std::cout << panaderia->Operation();
}

int main() {
  Horno* horno = new Horno;
  Empaque* empaque = new Empaque;
  Panaderia* panaderia = new Panaderia(horno, empaque);
  ClientCode(panaderia);
  delete panaderia;
  return 0;
}
Panaderia inicia los subsistemas:
Horno: listo!
Empaque: preparado!
Panaderia les ordena trabajar:
Horno: a cocinar!
Empaque: a embolsar!
RenglónLo que se veQué parte del patrón es
4Una clase con sus propias operaciones, que no hereda de nadie ni conoce a las demás.Una clase del subsistema
14Otra clase independiente, con operaciones distintas.Otra clase del subsistema: no comparten interfaz
26La tercera clase guarda un puntero a cada una de las otras dos (este renglón y el siguiente).Los atributos de la Fachada (Panaderia)
38Un solo método público, que llama a las operaciones de las dos en un orden fijo.La operación simple de la fachada
49El cliente recibe solo a la tercera clase y llama a un único método.El Cliente, que no conoce el subsistema

Respuesta: "Es el patrón Facade (estructural). Panaderia es la fachada: guarda punteros a Horno y Empaque, que son las clases del subsistema, y ofrece un único método Operation() que llama en orden a las operaciones de las dos. El cliente usa solo a Panaderia, sin conocer el subsistema. Las clases del subsistema no comparten interfaz ni conocen a la fachada."

Cambian los nombres, no la forma

Es el ejemplo de Facade de Refactoring.Guru (la fuente del apunte) con las clases rebautizadas: Subsystem1, Subsystem2 y Facade. Los métodos quedaron con su nombre original (Operation1, OperationN, OperationZ). Es el patrón que tomaron como código en los dos parciales, 2024 y 2025: están resueltos en Evaluación, y la guía trae otro en C# (Práctica, ejercicio 7).

Ejemplo 6 — Con formato de parcial: agregarlo a un diagrama

Inventado · con la forma de la Guía N°1, ejercicio 1

"Dado el siguiente diagrama de un banco: para hacer una transferencia, CajeroWeb usa directamente las clases Cuentas, Seguridad y Auditoria. Se va a sumar una AppMovil que necesita hacer las mismas transferencias. Modifique el diagrama para que los dos clientes tengan una interfaz fácil y de simple acceso, sin repetir esa lógica. Justifique."

Qué hay en el diagrama. El cliente tiene tres flechas, una a cada clase del subsistema: conoce las tres y sabe en qué orden llamarlas. Si AppMovil se sumara así, serían otras tres flechas y la misma lógica escrita dos veces.

Qué se cambia, en orden:

  1. Agregar la Fachada entre el cliente y el subsistema. La clase Operaciones, con el método simple transferir(origen, destino, monto).
  2. Darle un atributo por cada clase del subsistema. cuentas, seguridad y auditoria, con una flecha de la fachada a cada una.
  3. Cortar las flechas del cliente al subsistema. CajeroWeb queda con una sola flecha, hacia Operaciones. Su método con toda la lógica ya no hace falta: la tiene la fachada.
  4. Sumar el cliente nuevo. AppMovil, también con una sola flecha hacia la fachada.

El diagrama modificado:

Justificación: "Se aplica Facade porque una transferencia obliga a coordinar tres clases y se pide un acceso simple. Operaciones guarda un objeto de cada una y ofrece transferir(), que valida al usuario, debita, acredita y registra la operación. CajeroWeb y AppMovil dependen solo de la fachada, así que la lógica queda en un solo lugar."

A tener en cuenta al modificar el diagrama
  • Las clases del subsistema no se borran ni cambian, y no conocen a la fachada: todas las flechas salen de la fachada hacia ellas.
  • No hay interfaz común entre las clases del subsistema: cada una hace lo suyo. Es la diferencia con Composite y con Strategy.
  • El cliente no puede quedar con ninguna flecha directa al subsistema.
  • La fachada no agrega funciones nuevas: ordena las que ya había.

Errores y trampas

Con qué se confunde
  • Con Adapter: el Adapter envuelve una clase y hereda de una interfaz que el cliente ya usaba. La Facade envuelve varias y no hereda de nada.
  • Con Composite: los dos tienen una clase que les pasa el trabajo a otras. En Composite las otras son del mismo tipo que ella (una lista de componentes); en Facade son clases distintas, una de cada una.
La fachada no agrega funciones

Solo ordena y simplifica lo que el subsistema ya sabía hacer. Y no lo encierra: quien necesite algo más fino puede seguir usando las clases del subsistema directamente.
