Creacional

1. Singleton

También llamado Instancia única.

Para qué sirve

Hay cosas de las que en un programa tiene que haber una sola: la configuración, la conexión a la base de datos, el registro de errores. Si cada parte del programa creara la suya, habría varias configuraciones distintas dando vueltas y nadie sabría cuál vale.

Singleton resuelve dos problemas a la vez:

  1. Garantiza que la clase tenga una única instancia (un solo objeto).
  2. Da un punto de acceso global a esa instancia: cualquier parte del programa puede pedirla, y siempre recibe la misma.
Propósito

Singleton es un patrón creacional que asegura que una clase tenga una única instancia y proporciona un punto de acceso global a ella.

La idea de la solución

Dos movimientos, y los dos ya se vieron en la Unidad 0, sección 3:

  1. El constructor se hace privado. Así nadie de afuera puede escribir new: la única que puede crear el objeto es la propia clase.
  2. Se agrega un método estático que hace de puerta: la primera vez que lo llaman crea el objeto y lo guarda en un atributo estático; todas las veces siguientes devuelve ese mismo objeto guardado.

Analogía del apunte: el gobierno de un país. Un país tiene un solo gobierno oficial y, cambien quienes cambien las personas, "el Gobierno de X" es el punto de acceso global para saber quién está a cargo.

Ejemplo 1 — En C++: la configuración de una aplicación

El programa, en 7 partes. Los números de la izquierda son los renglones del programa completo; los renglones resaltados son los que hay que mirar.

1Las bibliotecas

#include <iostream>
#include <string>

2El casillero y el constructor privadoSingleton

class Configuracion {
 private:
  static Configuracion* instancia_;
  std::string idioma_;

  Configuracion() : idioma_("es") {}

Las dos primeras piezas: el atributo estático instancia_, donde se guarda el único objeto, y el constructor debajo de private:, que nadie de afuera puede usar.

3Prohibir las copias

 public:
  Configuracion(const Configuracion&) = delete;
  void operator=(const Configuracion&) = delete;

= delete se lee "esto no se puede hacer". Sin copias no hay un segundo objeto.

4La puerta: el método estáticoSingleton

  static Configuracion* obtenerInstancia() {
    if (instancia_ == nullptr) {
      instancia_ = new Configuracion;
    }
    return instancia_;
  }

La tercera pieza. La primera vez crea el objeto; todas las demás devuelve el que ya estaba.

5El trabajo propio de la clase

  std::string idioma() const {
    return idioma_;
  }

  void cambiarIdioma(std::string idioma) {
    idioma_ = idioma;
  }
};

Un Singleton sigue siendo una clase común: además de controlar su instancia, hace su trabajo.

6El valor inicial del atributo estático

Configuracion* Configuracion::instancia_ = nullptr;

Al arrancar no apunta a nada.

7El programa

int main() {
  Configuracion* a = Configuracion::obtenerInstancia();
  Configuracion* b = Configuracion::obtenerInstancia();

  std::cout << b->idioma() << "\n";
  a->cambiarIdioma("en");
  std::cout << b->idioma() << "\n";

  if (a == b) {
    std::cout << "a y b son el mismo objeto\n";
  }
  return 0;
}

Se pide la instancia dos veces y se comprueba que es la misma.

Cómo reconocerlo

DóndeQué lo delata
En un enunciado"una sola instancia", "se debe poder crear sólo una instancia", "existe un único objeto encargado de...", "que todas las partes de la aplicación compartan el mismo registro", "una lista única".
En un código Tres señales, que aparecen juntas:
  1. un atributo static que es un puntero a la propia clase;
  2. el constructor debajo de private: o protected:;
  3. un método static (casi siempre GetInstance) con un if (... == nullptr) que hace el new y devuelve el atributo.
Suelen acompañar las dos líneas con = delete.

Ventajas y desventajas

VentajasDesventajas
  • Se tiene la certeza de que la clase tiene una única instancia.
  • Hay un punto de acceso global a esa instancia.
  • El objeto se crea recién cuando se pide por primera vez.
  • Vulnera el principio de responsabilidad única: la clase resuelve dos problemas a la vez (su trabajo y controlar su propia creación).
  • Puede enmascarar un mal diseño: partes del programa que saben demasiado unas de otras.
  • Necesita un cuidado especial con varios hilos, para que dos hilos no creen el objeto dos veces.
  • Complica las pruebas unitarias del código que lo usa.

Dónde se usa

  • La conexión a la base de datos, compartida por todo el sistema.
  • La configuración global de una aplicación (idioma, tema).
  • El registro de eventos (log) donde todas las partes anotan errores.
  • Un gestor de usuarios o de seguridad único para todo el sistema.

Ejemplo 2 — Con formato de parcial: dibujarlo y explicarlo

Inventado · con la forma del Parcial 2024, ejercicio 2

"Realice el diagrama (mediante UML) del patrón Singleton, dé una breve descripción de su usabilidad y mencione 2 ejemplos."

La consigna pide tres cosas; la respuesta tiene que tener las tres:

  1. El diagrama: una sola clase, con el atributo instancia privado y estático (subrayado), el constructor privado y el método obtenerInstancia() público y estático (subrayado).
  2. La descripción: "Singleton es un patrón creacional que se usa cuando una clase debe tener una única instancia disponible para todo el programa. La clase oculta su constructor y ofrece un método estático que crea el objeto la primera vez y devuelve siempre el mismo. Así todo el programa usa el mismo objeto, a través de un único punto de acceso."
    Tiene tres oraciones: cuándo se usa, cómo funciona y qué se gana. Son las mismas que sirven después para justificar: solo se cambian las palabras generales por los nombres del caso.
  3. Dos ejemplos: no alcanza con nombrarlos. A cada uno se le suma una línea que diga por qué ahí va el patrón:
    • La conexión a la base de datos de un sistema. "Abrir una conexión es costoso y todos los módulos tienen que trabajar sobre la misma. Con la clase Conexion como Singleton, cualquier parte del sistema la pide y recibe siempre el mismo objeto."
    • La configuración global de una aplicación. "El idioma o la moneda tienen que valer lo mismo en todas las pantallas. Con una única Configuracion, si una pantalla cambia el idioma, las demás lo ven cambiado."

Ejemplo 4 — Con formato de parcial: identificar los patrones de un enunciado

Inventado · con la forma del Parcial 2025, Práctica 1

"A partir del siguiente enunciado identifique cuáles serían los patrones de diseño que utilizaría y justifique por qué eligió los mismos."

"La Biblioteca Popular Sarmiento está desarrollando un sistema para gestionar sus préstamos. Todos los módulos (préstamos, socios, catálogo) necesitan leer los mismos parámetros de funcionamiento: días máximos de préstamo, monto de la multa diaria y horario de atención. Se detectó que cada módulo cargaba su propia copia de esos parámetros y que a veces trabajaban con valores distintos, por lo que se requiere que exista un único objeto de configuración en todo el sistema, accesible desde cualquier módulo."

"Para registrar un préstamo, el bibliotecario hoy tiene que operar con tres módulos por separado y en un orden determinado: verificar que el socio no tenga deudas, comprobar la disponibilidad del ejemplar y registrar la fecha de devolución. Se busca que la pantalla de atención al público cuente con una interfaz sencilla, con una única operación para prestar un libro, que resuelva internamente todos esos pasos sin que el bibliotecario deba conocer cada módulo."

"Por último, cuando un libro que estaba prestado es devuelto, el sistema debe avisar automáticamente a todos los socios que lo tenían reservado. Los socios pueden anotarse o borrarse de la lista de espera de un libro en cualquier momento, y en el futuro se prevé avisar también al área de compras."

El enunciado mezcla Singleton con otros dos patrones, como en el parcial. El método: un párrafo, una necesidad, un patrón. En cada párrafo se busca qué se necesita y la frase que lo dice.

PárrafoLa necesidadLa frase que lo delataPatrón
1. La configuraciónQue todos los módulos usen los mismos parámetros"exista un único objeto de configuración en todo el sistema, accesible desde cualquier módulo"Singleton (creacional)
2. El préstamoHacer con una sola operación lo que hoy son tres pasos en tres módulos"una interfaz sencilla, con una única operación (...) sin que el bibliotecario deba conocer cada módulo"Facade (estructural)
3. Las reservasQue los socios se enteren solos cuando el libro vuelve"avisar automáticamente a todos los socios que lo tenían reservado (...) pueden anotarse o borrarse"Observer (de comportamiento)
Cómo quedaría escrita la respuesta

Singleton, que es el patrón de esta sección, con sus tres partes:

  1. Qué patrón y por qué: "Usaría Singleton, un patrón creacional, porque la clase de configuración debe tener una única instancia disponible para todo el programa: hoy cada módulo carga su propia copia y trabajan con valores distintos. El enunciado lo pide: "exista un único objeto de configuración en todo el sistema, accesible desde cualquier módulo"."
  2. Cómo se aplica: "La clase Configuracion oculta su constructor (es privado) y ofrece un método estático, obtenerInstancia(), que crea el objeto la primera vez y devuelve siempre el mismo, guardado en un atributo estático."
  3. Qué se gana: "Préstamos, socios y catálogo usan el mismo objeto, a través de un único punto de acceso, y leen siempre los mismos valores."

Los otros dos patrones, más breves:

  • Facade (estructural), para registrar un préstamo. Se usa cuando para hacer una tarea hay que coordinar varias clases de un subsistema, y acá hoy hay que "operar con tres módulos por separado y en un orden determinado". Una fachada guarda un objeto de cada una y ofrece una operación simple, prestar un libro, que las llama en el orden correcto.
  • Observer (de comportamiento), para las reservas. Se usa cuando un cambio en un objeto se tiene que avisar a otros, sin saber de antemano cuántos ni cuáles son, y acá hay que "avisar automáticamente a todos los socios que lo tenían reservado", que "pueden anotarse o borrarse de la lista de espera". El libro es el notificador: guarda una lista de suscriptores y les avisa a todos.

Dibujado. La consigna no lo pide, pero así queda el diagrama de Singleton de este enunciado (los nombres de las clases los elige uno):

Las trampas de este enunciado
  • En el primer párrafo no aparece la palabra "crear": la pista de este creacional es la cantidad de objetos ("un único").
  • "Interfaz sencilla" no es Adapter: no hay nada incompatible que adaptar, hay varios módulos que coordinar. Es Facade.

Ejemplo 5 — Con formato de parcial: reconocerlo en un código

Inventado · con la forma de la Guía N°1, ejercicio 2

"Dado el siguiente código identifique qué tipo de patrón se implementa. Justifique."

Los renglones resaltados son los que lo delatan:

#include <iostream>
#include <string>

class Bitacora {
 protected:
  Bitacora() {}
  static Bitacora* bitacora_;

 public:
  Bitacora(Bitacora &otra) = delete;
  void operator=(const Bitacora &) = delete;

  static Bitacora *GetInstance();

  void Registrar(const std::string& texto) const {
    std::cout << "[bitacora] " << texto << "\n";
  }
};

Bitacora* Bitacora::bitacora_ = nullptr;

Bitacora *Bitacora::GetInstance() {
  if (bitacora_ == nullptr) {
    bitacora_ = new Bitacora();
  }
  return bitacora_;
}

int main() {
  Bitacora::GetInstance()->Registrar("inicio de sesion");
  Bitacora::GetInstance()->Registrar("cierre de sesion");
  return 0;
}

[bitacora] cierre de sesion

7Un atributo static del mismo tipo que la clase.La única instancia
10Se prohíbe copiar el objeto (y, en el renglón siguiente, asignarlo).Un refuerzo: que no aparezca una segunda instancia por copia

Respuesta: "Es el patrón Singleton (creacional). La clase Bitacora oculta su constructor y guarda en el atributo estático bitacora_ su única instancia. El método estático GetInstance() la crea la primera vez y después devuelve siempre la misma, de modo que todo el programa escribe en la misma bitácora."

Cambian los nombres, no la forma

Es el Singleton de Refactoring.Guru (la fuente del apunte) con la clase rebautizada. El método quedó con su nombre original, GetInstance: cuando un método conserva el nombre en inglés del ejemplo, es una pista. La guía trae este mismo código con la clase Inicio_Serie (Práctica, ejercicio 1).

Ejemplo 6 — Con formato de parcial: agregarlo a un diagrama

Guía N°1 · ejercicio 1 (primer pedido)

"Considere el siguiente diagrama de UML, el cual modela un módulo de seguridad de una aplicación. Dada esta implementación se necesita: se debe poder crear sólo una instancia de la clase ControladorSeguridad, ya que existe un único objeto encargado de realizar dicha tarea."

"Indicar qué patrón se puede utilizar y justificar su uso. Reescribir el diagrama de UML con la solución implementada."

Qué hay en el diagrama. Cuatro clases unidas por líneas simples. ControladorSeguridad no muestra constructor: en UML, si no se dibuja, se entiende que es público y cualquiera puede crear los controladores que quiera. El ejercicio tiene un segundo pedido, sobre el Logger: es Observer y está resuelto en la Unidad 4C, sección 1.

Qué se cambia, en orden:

  1. Agregar el atributo estático. En ControladorSeguridad, - instancia: ControladorSeguridad, privado y subrayado. El atributo sesionesActivas que ya tenía queda igual.
  2. Dibujar el constructor, privado. - ControladorSeguridad(). En el diagrama original no estaba; ahora hay que dibujarlo para mostrar que nadie de afuera puede crear otro.
  3. Agregar el método estático. + obtenerInstancia(): ControladorSeguridad, público y subrayado.
  4. Dejar el resto como está. Usuario, Sesion y Logger no cambian, y registrarAcceso() sigue siendo un método común.

El diagrama modificado:

Justificación: "Se utiliza Singleton porque ControladorSeguridad debe tener una única instancia disponible para todo el programa: el enunciado pide "poder crear sólo una instancia de la clase ControladorSeguridad". La clase oculta su constructor (pasa a ser privado) y ofrece un método estático, obtenerInstancia(), que crea el objeto la primera vez y devuelve siempre el mismo. Así todo el sistema registra los accesos en el mismo controlador."

A tener en cuenta al modificar el diagrama
  • No se agrega ninguna clase. Singleton modifica una que ya está: en total son tres renglones nuevos en una caja.
  • Los dos miembros estáticos van subrayados. Sin el subrayado no se ve que son de la clase, y es lo que define al patrón.
  • El constructor tiene que quedar dibujado con el signo -, aunque el diagrama original no lo mostrara.
  • La consigna dice "patrón / patrones": son dos pedidos y dos patrones. En la hoja van los dos sobre el mismo diagrama.

Errores y trampas

Crear el objeto con new desde afuera no compila

Si en main se escribe Configuracion c;:

error: 'Configuracion::Configuracion()' is private within this context

Ese error es justamente el patrón funcionando: la única forma de llegar al objeto es obtenerInstancia().

No es lo mismo que una variable global

Una variable global también se ve desde todos lados, pero cualquiera puede pisarla o crear otro objeto igual. El Singleton garantiza que haya uno solo y que nadie lo reemplace.

Lo que más se olvida en el dibujo

Que el constructor es privado. Sin eso, el diagrama muestra una clase común con un método estático, y nada impide crear más objetos.
