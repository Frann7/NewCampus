3. Abstract Factory

También llamado Fábrica Abstracta.

Para qué sirve

El problema, con el ejemplo del apunte: una tienda de muebles.

  • Vende varios productos: silla, sofá, mesilla.
  • Cada producto viene en varias variantes (estilos): moderna, victoriana, art déco.
  • El cliente quiere muebles que combinen: si pide un juego moderno, no puede llegarle una silla moderna con un sofá victoriano.
  • Los catálogos cambian seguido: hay que poder agregar variantes sin tocar el código que ya funciona.

Un conjunto de productos que van juntos (silla moderna + sofá moderno + mesilla moderna) es una familia. Abstract Factory pone la creación de toda una familia en un solo objeto, la fábrica: quien usa la fábrica moderna recibe siempre muebles modernos.

Propósito

Abstract Factory es un patrón creacional que permite producir familias de objetos relacionados sin especificar sus clases concretas.

La idea de la solución

Conviene armar primero la tabla de productos y variantes:

SillaSofá
ModernaSillaModernaSofaModerno
VictorianaSillaVictorianaSofaVictoriano
  1. Cada columna es una interfaz de producto (Silla, Sofa): todas las sillas se usan igual, sean del estilo que sean.
  2. Cada fila es una fábrica concreta (FabricaModerna, FabricaVictoriana): crea todos los productos de esa variante.
  3. Todas las fábricas cumplen una misma interfaz, la fábrica abstracta, que tiene un método de creación por cada columna: crearSilla() y crearSofa().
  4. El cliente recibe una fábrica y le pide los muebles. No sabe cuál fábrica es ni qué clases concretas le devuelve.

Estructura

ParteQué esEn el ejemplo de los muebles
Productos AbstractosUna interfaz por cada tipo de producto de la familia.Silla, Sofa
Productos ConcretosLas implementaciones de cada producto, una por variante.SillaModerna, SillaVictoriana, SofaModerno, SofaVictoriano
Fábrica Abstracta (Abstract Factory)La interfaz con un método de creación por cada producto abstracto.FabricaDeMuebles, con crearSilla() y crearSofa()
Fábricas ConcretasUna por variante. Cada una crea solo los productos de su variante.FabricaModerna, FabricaVictoriana
ClienteUsa la fábrica y los productos solo a través de las interfaces.El código que amuebla

Cómo dibujarlo de memoria:

  • A la izquierda, las fábricas: la interfaz arriba y una fábrica concreta por variante abajo.
  • A la derecha, los productos: una interfaz por producto, cada una con sus concretos abajo.
  • Las flechas punteadas "crea" salen de la fábrica hacia cada interfaz de producto: los métodos de la fábrica devuelven el producto abstracto, aunque por dentro cada fábrica concreta haga el new del concreto de su variante (FabricaConcreta1 crea ProductoA1 y ProductoB1).
  • El Cliente guarda una fábrica (flecha continua hacia la interfaz).

Ejemplo 1 — En C++: la mueblería

El programa, en 7 partes. Los números de la izquierda son los renglones del programa completo; los renglones resaltados son los que hay que mirar.

1Las bibliotecas

#include <iostream>
#include <string>

2Una interfaz por cada tipo de muebleProductos abstractos

class Silla {
 public:
  virtual ~Silla() {}
  virtual std::string describir() const = 0;
};

class Sofa {
 public:
  virtual ~Sofa() {}
  virtual std::string describir() const = 0;
};

Dos interfaces distintas: Silla y Sofa.

3Cada mueble en cada estiloProductos concretos

class SillaModerna : public Silla {
 public:
  std::string describir() const override { return "silla moderna"; }
};

class SofaModerno : public Sofa {
 public:
  std::string describir() const override { return "sofa moderno"; }
};

class SillaVictoriana : public Silla {
 public:
  std::string describir() const override { return "silla victoriana"; }
};

class SofaVictoriano : public Sofa {
 public:
  std::string describir() const override { return "sofa victoriano"; }
};

Dos productos por dos variantes: cuatro clases.

4La interfaz de las fábricasFábrica abstracta

class FabricaDeMuebles {
 public:
  virtual ~FabricaDeMuebles() {}
  virtual Silla* crearSilla() const = 0;
  virtual Sofa* crearSofa() const = 0;
};

Un método de creación por producto. Cada uno devuelve la interfaz, no una clase concreta.

5Una fábrica por estiloFábricas concretas

class FabricaModerna : public FabricaDeMuebles {
 public:
  Silla* crearSilla() const override { return new SillaModerna; }
  Sofa* crearSofa() const override { return new SofaModerno; }
};

class FabricaVictoriana : public FabricaDeMuebles {
 public:
  Silla* crearSilla() const override { return new SillaVictoriana; }
  Sofa* crearSofa() const override { return new SofaVictoriano; }
};

Todo lo que crea cada una es de su estilo: por eso los muebles combinan.

6El que usa la fábricaCliente

void amoblar(FabricaDeMuebles* fabrica) {
  Silla* silla = fabrica->crearSilla();
  Sofa* sofa = fabrica->crearSofa();
  std::cout << "Juego: " << silla->describir() << " + " << sofa->describir() << "\n";
  delete silla;
  delete sofa;
}

Recibe una fábrica cualquiera y le pide los muebles. No nombra ninguna clase concreta.

7El programa

int main() {
  FabricaDeMuebles* f = new FabricaModerna;
  amoblar(f);
  delete f;

  f = new FabricaVictoriana;
  amoblar(f);
  delete f;
  return 0;
}

El estilo se elige una sola vez, al crear la fábrica.

Qué imprime y por qué

Juego: silla moderna + sofa moderno
Juego: silla victoriana + sofa victoriano

Nunca sale "silla moderna + sofa victoriano": es imposible, porque cada fábrica solo sabe crear los productos de su variante. Para agregar el estilo art déco se suman tres clases (SillaArtDeco, SofaArtDeco, FabricaArtDeco) y amoblar no se toca.

Cómo reconocerlo

DóndeQué lo delata
En un enunciadoLa palabra "familias": "la creación flexible de familias de objetos", "diferentes familias de productos". O varios productos que tienen que ajustarse todos a una misma variante: "crear diferentes tipos de elementos de interfaz de usuario, como botones y cuadros de texto, de manera que se ajusten a la plataforma específica (escritorio o web)".
En un código
  1. una interfaz con varios métodos de creación (CreateProductA, CreateProductB...) que devuelven punteros a distintas clases base;
  2. dos o más jerarquías de productos (una clase base por producto);
  3. varias clases que cumplen la interfaz fábrica y cuyos métodos son return new ...; de productos de la misma variante;
  4. un cliente que recibe la fábrica por parámetro y le pide los productos.

Ventajas y desventajas

VentajasDesventajas
  • Se tiene la certeza de que los productos que salen de una fábrica son compatibles entre sí.
  • Evita un acoplamiento fuerte entre los productos concretos y el código cliente.
  • Principio de responsabilidad única: el código de creación queda en un solo lugar.
  • Principio de abierto/cerrado: se agregan variantes nuevas sin romper el código cliente.
  • El código se puede complicar más de lo necesario: aparecen muchas interfaces y clases nuevas.

Dónde se usa

  • Interfaces de usuario multiplataforma (el otro ejemplo del apunte): botones y casillas que se ven distinto en Windows y en Mac, con una fábrica por sistema operativo.
  • Catálogos por estilo o por línea: los muebles del ejemplo.
  • Cualquier sistema que deba funcionar con varias familias de productos relacionados sin depender de sus clases concretas, porque no se conocen de antemano o porque se quiere poder agregar más.

Ejemplo 2 — Con formato de parcial: dibujarlo y explicarlo

Parcial 2025 · Teoría 4 (20 puntos, con Adapter)

Del enunciado: "El equipo de desarrollo trabaja con Programación Orientada a Objetos (POO) y planea incorporar dos patrones de diseño en su solución empresarial, la creación flexible de familias de objetos y otro para conectar módulos con interfaces incompatibles con los existentes del sistema."

La consigna: "Represente mediante un diagrama UML la estructura de los patrones de diseño que quiere incorporar SoftMetrics. Explique el propósito de cada uno dentro del sistema."

Paso 1 — Descubrir cuáles son. El enunciado no los nombra: los describe.

Frase del enunciadoQué significaPatrón
"la creación flexible de familias de objetos"Es creacional, y la palabra "familias" es la del propósito de Abstract FactoryAbstract Factory
"conectar módulos con interfaces incompatibles"Es estructural: hacer que encajen clases que no encajanAdapter (Unidad 4B)

Paso 2 — El diagrama. Piden la estructura, así que va el diagrama general del patrón: Cliente, Fábrica Abstracta, dos Fábricas Concretas, dos Productos Abstractos y sus Productos Concretos.

Paso 3 — El propósito "dentro del sistema". Hay que atarlo a la empresa del enunciado, no recitar la definición sola:

"Abstract Factory permite crear familias de objetos relacionados sin especificar sus clases concretas. En SoftMetrics, que desarrolla soluciones web y aplicaciones empresariales, serviría para que cada tipo de solución tenga su fábrica (por ejemplo FabricaWeb y FabricaEscritorio) que cree todos sus componentes (botones, formularios, reportes) compatibles entre sí. El resto del sistema trabaja solo con las interfaces, así que se puede agregar una familia nueva sin modificar el código existente."

Si además pidieran dos ejemplos (como la consigna de 2024 con Singleton), cada uno con una línea que diga por qué ahí va el patrón:

  • Una mueblería. "Vende sillas, sofás y mesas en estilo moderno o victoriano, y los muebles de un pedido tienen que combinar. Una fábrica por estilo crea todos los muebles de ese estilo: nunca sale una silla moderna con un sofá victoriano."
  • Una interfaz gráfica multiplataforma. "Los botones y las casillas tienen el aspecto de Windows o el de Mac. La aplicación recibe la fábrica del sistema en el que corre y le pide todos los componentes, que salen del mismo aspecto."

Ejemplo 3 — Con formato de parcial: aplicarlo a un enunciado

Con la forma del Parcial 2025 · Práctica 1

"Un sistema de facturación se vende en Argentina y en Chile. En cada país cambian la Factura y el Recibo: tienen otro formato y otros impuestos. Los comprobantes de un mismo país se tienen que usar siempre juntos, y la empresa planea sumar más países sin modificar el código que emite los comprobantes. Indique qué patrón de diseño aplicaría, justifique y realice el diagrama UML."

Frase del enunciadoQué significaParte del patrón
"cambian la Factura y el Recibo"Hay dos tipos de producto distintosDos Productos Abstractos: Factura y Recibo
"se vende en Argentina y en Chile"Cada producto tiene una variante por paísLos Productos Concretos: FacturaArgentina, FacturaChilena, ReciboArgentino, ReciboChileno
"los comprobantes de un mismo país se tienen que usar siempre juntos"Son familias: no se pueden mezclarUna Fábrica Concreta por país, que crea la familia entera
"sumar más países sin modificar el código que emite"El que emite no puede nombrar clases concretasEl Cliente (Facturador) conoce solo la Fábrica Abstracta y las interfaces

Justificación: "Se aplica Abstract Factory porque hay familias de productos relacionados (la factura y el recibo de cada país) que no se pueden mezclar. FabricaFiscal declara un método de creación por cada producto y cada fábrica concreta devuelve los de su país. Facturador trabaja solo con las interfaces, así que sumar un país es agregar una fábrica y sus dos comprobantes, sin modificar lo que ya existe."

Por qué no es Factory Method: no se crea un solo tipo de cosa, sino dos que tienen que combinar.

Ejemplo 4 — Con formato de parcial: reconocerlo en un código

Con la forma del Parcial 2024 · ejercicio 4

"A partir del siguiente código identifique qué patrón es el que se utiliza. Justifique."

Los renglones resaltados son los que lo delatan:

#include <iostream>
#include <string>

class Motor {
 public:
  virtual ~Motor() {}
  virtual std::string UsefulFunctionA() const = 0;
};
class MotorDeportivo : public Motor {
 public:
  std::string UsefulFunctionA() const override { return "motor deportivo"; }
};
class MotorUrbano : public Motor {
 public:
  std::string UsefulFunctionA() const override { return "motor urbano"; }
};

class Rueda {
 public:
  virtual ~Rueda() {}
  virtual std::string UsefulFunctionB() const = 0;
};
class RuedaDeportiva : public Rueda {
 public:
  std::string UsefulFunctionB() const override { return "rueda deportiva"; }
};
class RuedaUrbana : public Rueda {
 public:
  std::string UsefulFunctionB() const override { return "rueda urbana"; }
};

class FabricaDePartes {
 public:
  virtual ~FabricaDePartes() {}
  virtual Motor* CreateMotor() const = 0;
  virtual Rueda* CreateRueda() const = 0;
};

class FabricaDeportiva : public FabricaDePartes {
 public:
  Motor* CreateMotor() const override { return new MotorDeportivo(); }
  Rueda* CreateRueda() const override { return new RuedaDeportiva(); }
};

class FabricaUrbana : public FabricaDePartes {
 public:
  Motor* CreateMotor() const override { return new MotorUrbano(); }
  Rueda* CreateRueda() const override { return new RuedaUrbana(); }
};

void ClientCode(const FabricaDePartes& fabrica) {
  const Motor* motor = fabrica.CreateMotor();
  const Rueda* rueda = fabrica.CreateRueda();
  std::cout << motor->UsefulFunctionA() << " + " << rueda->UsefulFunctionB() << "\n";
  delete motor;
  delete rueda;
}

int main() {
  FabricaDeportiva* deportiva = new FabricaDeportiva();
  ClientCode(*deportiva);
  FabricaUrbana* urbana = new FabricaUrbana();
  ClientCode(*urbana);
  delete deportiva;
  delete urbana;
  return 0;
}

motor urbano + rueda urbana

Respuesta: "Es el patrón Abstract Factory (creacional). FabricaDePartes es la fábrica abstracta: declara un método de creación por cada producto (CreateMotor() y CreateRueda()). FabricaDeportiva y FabricaUrbana son las fábricas concretas: cada una devuelve el motor y la rueda de su misma línea, que es la familia. ClientCode() trabaja solo con las interfaces, así que nunca mezcla un motor deportivo con una rueda urbana."

La cuenta que lo separa de Factory Method

Mirá cuántos métodos de creación tiene la clase base. Uno (y un solo producto): Factory Method. Dos o más, que devuelven productos distintos que van juntos: Abstract Factory.

Ejemplo 5 — Con formato de parcial: agregarlo a un diagrama

Con la forma del Parcial 2024 · ejercicio 3

"Dado el siguiente diagrama de un restaurante: la clase Cocina arma cada pedido creando directamente la entrada y el plato, según la línea que pidió el cliente. Ya ocurrió que salió una entrada vegana con un plato clásico, y además se va a sumar una línea sin TACC. Modifique el diagrama para que la entrada y el plato de un pedido sean siempre de la misma línea y se puedan agregar líneas nuevas sin modificar Cocina. Justifique."

Qué hay en el diagrama. Cocina tiene cuatro flechas "crea", una a cada clase concreta. Mirando los nombres hay dos tipos de producto (entrada y plato) en dos líneas (vegana y clásica): son dos familias, pero el diagrama no lo dice en ningún lado.

Qué se cambia, en orden:

  1. Una interfaz por cada tipo de producto. Entrada y Plato. EntradaVegana y EntradaClasica cumplen Entrada; PlatoVegano y PlatoClasico cumplen Plato.
  2. La Fábrica Abstracta. La interfaz FabricaDeMenu, con un método de creación por cada producto: crearEntrada(): Entrada y crearPlato(): Plato.
  3. Una Fábrica Concreta por cada familia. FabricaVegana y FabricaClasica, que cumplen FabricaDeMenu. Cada una crea los dos productos de su línea.
  4. El cliente guarda una fábrica. Cocina gana el atributo - fabrica: FabricaDeMenu y una flecha hacia esa interfaz. Se borran sus cuatro flechas a las clases concretas.
  5. Las flechas "crea". Punteadas, de FabricaDeMenu a Entrada y a Plato.

El diagrama modificado:

Justificación: "Se aplica Abstract Factory porque la entrada y el plato de cada línea forman una familia que no se debe mezclar. Cocina recibe una FabricaDeMenu y le pide los dos productos: como una fábrica concreta solo crea los de su línea, el pedido sale siempre consistente. La línea sin TACC se agrega con una fábrica y dos productos nuevos, sin modificar Cocina."

A tener en cuenta al modificar el diagrama
  • Tres cuentas para no olvidarse cajas: tantas interfaces de producto como tipos de producto (2), tantos métodos en la fábrica como tipos de producto (2), tantas fábricas concretas como familias (2).
  • Las clases que ya estaban no se borran ni se renombran: pasan a ser los productos concretos.
  • El cliente no puede quedar con ninguna flecha hacia una clase concreta.
  • Si el enunciado tuviera un solo tipo de producto, sería Factory Method.

Errores y trampas

Una sola jerarquía de productos no es Abstract Factory

Si la fábrica tiene un solo método de creación y hay un solo tipo de producto, es Factory Method. Abstract Factory necesita al menos dos productos distintos que formen familia.

Cuidado con qué se cuenta como fábrica

Hay una fábrica concreta por variante (moderna, victoriana), no por producto (silla, sofá). Si te encontrás dibujando FabricaDeSillas y FabricaDeSofas, las familias están al revés.

Agregar un producto nuevo sí obliga a tocar todo

Agregar una variante (art déco) es fácil: una fábrica más. Agregar un producto (mesilla) obliga a sumar un método a la fábrica abstracta y a todas las concretas.
