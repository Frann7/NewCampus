Formulario con token y el script que lo verifica

Carpeta formularios: inicio.php (menú), includes/head.php y includes/footer.php (encabezado y pie comunes), formToken.php (el formulario con token), formCaptcha.php e includes/rdnimg.php (el captcha, en el ejemplo siguiente) y procesoForm.php, que recibe los dos formularios.

Archivos 1 y 2 — includes/head.php e includes/footer.php

head.php tiene el principio de toda página: <!DOCTYPE html>, el <head> con Bootstrap, la apertura de <body> y de un <div class="container">, y una barra de navegación con tres enlaces: 

<li class="nav-item active">
    <a class="nav-link" href="inicio.php">Inicio <span class="sr-only">(current)</span></a>
</li>
<li class="nav-item">
    <a class="nav-link" href="formToken.php">Formulario con Token</a>
</li>
<li class="nav-item">
    <a class="nav-link" href="formCaptcha.php">Formulario con Captcha</a>
</li>

footer.php cierra lo que abrió head.php: el </div> del contenedor, los <script> de Bootstrap (jQuery, Popper y Bootstrap, que hacen funcionar el menú plegable en pantallas chicas), </body> y </html>. Ninguno de los dos tiene código PHP: son HTML que las páginas traen con require_once (teoría, sección 8).

Qué se ve

El menú, el título y el formulario, con un campo de texto arriba que ya trae escrito el token (en la prueba, jbC6lszckXPiToFxyQEr). Cada vez que se recarga la página, el token cambia.

Archivo 5 — procesoForm.php (la parte del token) 
<?php
session_start();

if (!empty($_POST)) {

    //---- PROCESO EL FORM-TOKEN ----

    if (!empty($_POST['token'])) {
        if ($_POST['token'] == $_SESSION['token']) {
            echo "LOS DATOS PROVIENEN DE NUESTRO FORMULARIO CON TOKEN.";

            // proceso los datos restantes

            echo '<br>';
            echo 'Usuario: ' . $_POST['usuario'];
            echo '<br>';
            echo 'Contraseña: ' . $_POST['contrasenia'];
        } else {
            echo "LOS DATOS PROVIENEN DE OTRO ORIGEN.";
        }
    }

    // (después sigue la parte del captcha: ejemplo siguiente)
}
?>

Qué hace cada línea

LíneaQué hace
session_start();Reanuda la sesión del navegador que envió: así aparece $_SESSION['token'].
if (!empty($_POST))Solo trabaja si llegó un POST.
if (!empty($_POST['token']))Solo si vino un token. Así sabe que el envío es del formulario con token (el del captcha no manda ese campo).
$_POST['token'] == $_SESSION['token']Compara lo enviado con lo guardado.
rama del ifCoinciden: avisa y muestra los datos (acá iría guardarlos).
rama del elseNo coinciden: avisa y no muestra nada más.

Qué problema de seguridad evita, y cuál no
  • Evita el ataque de ataqueForm: un programa que manda datos sin haber abierto el formulario (caso 4) no se procesa.
  • Gracias al !empty($_POST['token']), no tiene el agujero de la versión del PDF (teoría, sección 5), donde un envío sin token pasaba.
  • No evita un programa que primero abra formToken.php guardando la cookie, copie el token del HTML y lo mande: es exactamente lo que se hizo en el caso 1 para probarlo. Y el token se puede reusar (caso 2). Para eso, el captcha.
Detalles del ejemplo
  • El token está en un campo type="text", visible. En la teoría va en un type="hidden"; acá se dejó a la vista para que se vea el código. Funciona igual, pero en un sitio real va oculto.
  • novalidate en el <form> le dice al navegador que no valide nada: el required del usuario no se aplica, y se puede enviar vacío. La clase needs-validation es de Bootstrap, para una validación con JavaScript que este ejemplo no incluye.
  • El caso 5 muestra el Warning porque XAMPP tiene display_errors=On. El script no se rompe: compara contra null y da false.
