Comportamiento

2. Strategy

También llamado Estrategia.

Para qué sirve

El problema, con el ejemplo del apunte: una aplicación de navegación.

  • La primera versión calculaba rutas en auto.
  • Después se agregaron las rutas a pie, y más tarde en transporte público, para ciclistas, turísticas...
  • Cada forma nueva se metía en la misma clase, que duplicaba su tamaño. Tocar un algoritmo podía romper los otros, y la clase era imposible de mantener.

Todas esas formas hacen lo mismo (calcular una ruta) de manera distinta. Strategy saca cada forma a su propia clase, todas con la misma interfaz, y la clase original se queda con una referencia a una de ellas y le pasa el trabajo. Para cambiar de forma se le cambia el objeto, incluso mientras el programa corre.

  • Cada forma de hacer la tarea es una estrategia.
  • La clase original, la que usa la estrategia, es el contexto.

Analogía del apunte: llegar al aeropuerto. Se puede ir en colectivo, en taxi o en bicicleta: son estrategias de transporte, y se elige una según el presupuesto o el tiempo que haya.

Propósito

Strategy es un patrón de comportamiento que permite definir una familia de algoritmos, colocar cada uno en una clase separada y hacer sus objetos intercambiables.

Un algoritmo, acá, es simplemente "una forma de hacer algo": de ordenar, de calcular un precio, de frenar, de armar una ruta.

Estructura

ParteQué esEn el ejemplo del navegador

Cómo dibujarlo de memoria:

  • A la izquierda el Contexto, con el atributo estrategia y el método para cambiarla.
  • Un rombo vacío del Contexto a la interfaz Estrategia (también se acepta una flecha simple): el contexto tiene una estrategia. Sin asterisco: es una sola por vez.
  • Debajo de la interfaz, las estrategias concretas, con línea punteada.
Se parece mucho al diagrama de Observer

Los dos son "una clase con un rombo hacia una interfaz, y clases concretas debajo". La diferencia está en el rombo y en los métodos: Observer tiene una lista (*) y los métodos suscribir, desuscribir y notificar; Strategy tiene una sola referencia y un método para cambiarla.

Ejemplo 1 — En C++: el navegador

El programa, en 5 partes. Los números de la izquierda son los renglones del programa completo; los renglones resaltados son los que hay que mirar.

1Las bibliotecas

#include <iostream>
#include <string>

2Lo que tienen en común las formas de hacerloEstrategia

class EstrategiaRuta {
 public:
  virtual ~EstrategiaRuta() {}
  virtual std::string calcularRuta(std::string origen, std::string destino) const = 0;
};

Toda forma de calcular una ruta recibe origen y destino y devuelve un texto.

3Las formas de hacerloEstrategias concretas

class RutaEnAuto : public EstrategiaRuta {
 public:
  std::string calcularRuta(std::string origen, std::string destino) const override {
    return "En auto de " + origen + " a " + destino + ": por la ruta, 20 minutos";
  }
};

class RutaAPie : public EstrategiaRuta {
 public:
  std::string calcularRuta(std::string origen, std::string destino) const override {
    return "A pie de " + origen + " a " + destino + ": por el camino costero, 3 horas";
  }
};

El mismo método, resuelto de dos maneras.

4La clase que usa unaContexto

class Navegador {
 private:
  EstrategiaRuta* estrategia_;

 public:
  Navegador(EstrategiaRuta* estrategia) : estrategia_(estrategia) {}

  void cambiarEstrategia(EstrategiaRuta* estrategia) {
    estrategia_ = estrategia;
  }

  void mostrarRuta(std::string origen, std::string destino) const {
    std::cout << estrategia_->calcularRuta(origen, destino) << "\n";
  }
};

Guarda un puntero a la interfaz, lo recibe desde afuera, lo puede cambiar y le delega el trabajo: el navegador no calcula nada.

5El programa

int main() {
  EstrategiaRuta* enAuto = new RutaEnAuto;
  EstrategiaRuta* aPie = new RutaAPie;

  Navegador navegador(enAuto);
  navegador.mostrarRuta("Parana", "Oro Verde");

  navegador.cambiarEstrategia(aPie);
  navegador.mostrarRuta("Parana", "Oro Verde");

  delete enAuto;
  delete aPie;
  return 0;
}

El mismo navegador, la misma llamada, los mismos datos; en el medio se le cambia la estrategia.

Mismo navegador, misma llamada, mismos datos: cambió el resultado porque cambió la estrategia. Para agregar la ruta en bicicleta se escribe una clase RutaEnBici, y Navegador no se toca.

Es el mismo esqueleto del Duenio y su mascota de la Unidad 0, sección 4: una clase que guarda un puntero a una interfaz, lo recibe por constructor, lo puede cambiar y le delega.

Cómo reconocerlo

DóndeQué lo delata
En un enunciadoVarias formas de hacer una misma cosa, entre las que se elige: "el sistema aplique automáticamente la estrategia de configuración más adecuada según sus elecciones", distintas formas de calcular un precio, un descuento, un envío, un ordenamiento; "poder cambiar de un algoritmo a otro". Suele aparecer junto a "según..." (según el cliente, según el tipo, según la opción elegida).
En un código
  1. una clase (Context) con un atributo que es un puntero a una interfaz, recibido en el constructor;
  2. un método para reemplazarlo (set_strategy, setStrategy);
  3. un método que le delega el trabajo: llama al único método de la interfaz (DoAlgorithm, execute);
  4. varias clases que cumplen la interfaz y hacen lo mismo de distinta forma (una ordena de menor a mayor, la otra al revés);
  5. en el código de prueba, el mismo contexto usado dos veces, cambiándole la estrategia en el medio.

Ventajas y desventajas

VentajasDesventajas
  • Se pueden intercambiar algoritmos dentro de un objeto durante la ejecución.
  • Se aíslan los detalles de un algoritmo del código que lo usa.
  • Se puede sustituir la herencia por composición (en vez de una subclase por cada variante, un objeto intercambiable).
  • Principio de abierto/cerrado: se agregan estrategias nuevas sin cambiar el contexto.
  • Si hay un par de algoritmos que casi no cambian, no se justifica complicar el programa con clases e interfaces nuevas.
  • Los clientes deben conocer las diferencias entre estrategias para elegir la adecuada.
  • Muchos lenguajes modernos permiten lo mismo con funciones anónimas, sin tantas clases.

Dónde se usa

  • Cuando se quieren usar distintas variantes de un algoritmo dentro de un objeto y poder cambiar de una a otra en ejecución: rutas, formas de ordenar, formas de pago.
  • Cuando hay muchas clases parecidas que solo difieren en cómo hacen cierta cosa: se saca esa cosa a una jerarquía aparte y las clases se unifican. Es el ejemplo de la guía: coches que solo difieren en cómo frenan.
  • Para separar la lógica de negocio de una clase de los detalles de un algoritmo: cálculo de envío, de impuestos, de descuentos.

Inventado · con la forma del Parcial 2024, ejercicio 2

"Realice el diagrama (mediante UML) del patrón Strategy, dé una breve descripción de su usabilidad y mencione 2 ejemplos."

La consigna pide tres cosas; la respuesta tiene que tener las tres:

  2. La descripción: "Strategy es un patrón de comportamiento que se usa cuando hay varias formas de hacer una misma tarea y se quiere poder cambiar de una a otra mientras el programa corre. Cada forma va en su propia clase, todas con la misma interfaz, y el contexto guarda una y le delega la tarea. Así se agregan formas nuevas sin modificar el contexto."
    Tiene tres oraciones: cuándo se usa, cómo funciona y qué se gana. Son las mismas que sirven después para justificar: solo se cambian las palabras generales por los nombres del caso.

    • Los descuentos de un sistema de ventas. "El total se calcula distinto según la promoción (sin descuento, en efectivo, mayorista). Cada cálculo va en su clase y la venta usa el que le asignan, sin un if por cada promoción."

Ejemplo 4 — Con formato de parcial: identificar los patrones de un enunciado

Inventado · con la forma del Parcial 2025, Práctica 1

"A partir del siguiente enunciado identifique cuáles serían los patrones de diseño que utilizaría y justifique por qué eligió los mismos."

"RutaSegura es una compañía de seguros. Una póliza puede cubrir bienes individuales o grupos de bienes, que a su vez contienen otros grupos (por ejemplo, una flota con sus sucursales y, dentro de cada una, sus vehículos). El sistema debe calcular el valor asegurado total de una póliza de la misma manera, se trate de un bien suelto o de un grupo completo."

"La prima que paga el cliente se calcula con distintos métodos de evaluación de riesgo (conservador, estándar y agresivo). El asesor selecciona el método para cada cliente en el momento de cotizar y puede cambiarlo durante la entrevista. La compañía planea incorporar nuevos métodos sin modificar el cotizador."

"Por cada póliza, el sistema emite un contrato y un certificado de cobertura. Ambos documentos existen en versión Particulares y en versión Empresas, y los de una versión no deben mezclarse con los de la otra. Próximamente se agregará la versión Agro."

El enunciado mezcla Strategy con otros dos patrones, como en el parcial. El método: un párrafo, una necesidad, un patrón. En cada párrafo se busca qué se necesita y la frase que lo dice.

PárrafoLa necesidadLa frase que lo delataPatrón
1. Los bienesTratar igual a un bien que a un grupo, que contiene bienes y más grupos"grupos de bienes, que a su vez contienen otros grupos (...) de la misma manera"Composite (estructural)
2. La primaVarias formas de calcular, que el asesor elige y cambia"distintos métodos de evaluación de riesgo (...) selecciona el método (...) y puede cambiarlo"Strategy (de comportamiento)
3. Los documentosCrear documentos que van juntos, y poder sumar versiones"un contrato y un certificado (...) los de una versión no deben mezclarse con los de la otra"Abstract Factory (creacional)
Cómo quedaría escrita la respuesta

Strategy, que es el patrón de esta sección, con sus tres partes:

  1. Qué patrón y por qué: "Usaría Strategy, un patrón de comportamiento, porque hay varias formas de hacer una misma tarea (calcular la prima) y se quiere poder cambiar de una a otra mientras el programa corre. El enunciado lo dice: hay "distintos métodos de evaluación de riesgo", y el asesor "selecciona el método" y "puede cambiarlo durante la entrevista"."
  2. Cómo se aplica: "Cada método va en su propia clase, una estrategia concreta: conservador, estándar y agresivo. Todas cumplen la misma interfaz, la estrategia: MetodoDeRiesgo. Cotizador es el contexto (la clase que usa una estrategia y le delega la tarea): guarda una y le pasa el cálculo; con cambiarMetodo() se la cambia."
  3. Qué se gana: "Se agregan métodos nuevos sin modificar el cotizador."

Los otros dos patrones, más breves:

  • Composite (estructural), para los bienes asegurados. Se usa cuando los objetos forman un árbol, con elementos simples y contenedores que agrupan elementos simples u otros contenedores, y acá hay "grupos de bienes, que a su vez contienen otros grupos". El bien y el grupo cumplen una misma interfaz, y el contenedor resuelve cada pedido pasándoselo a lo que contiene.
  • Abstract Factory (creacional), para los documentos de la póliza. Se usa cuando hay que crear familias de objetos relacionados, que tienen que combinar entre sí, y acá se emiten "un contrato y un certificado de cobertura", y "los de una versión no deben mezclarse con los de la otra". Una fábrica abstracta declara un método de creación por cada producto, y hay una fábrica concreta por cada versión.

Dibujado. La consigna no lo pide, pero así queda el diagrama de Strategy de este enunciado (los nombres de las clases los elige uno):

Las trampas de este enunciado
  • "Métodos de evaluación" que se eligen y se cambian son estrategias. No es Factory Method: no se crean objetos de distintos tipos, se elige cómo calcular.
  • En el tercer párrafo son dos documentos que van juntos (contrato y certificado): por eso es Abstract Factory y no Factory Method.

Ejemplo 5 — Con formato de parcial: reconocerlo en un código

Inventado · con la forma de la Guía N°1, ejercicio 2

"Dado el siguiente código identifique qué tipo de patrón se implementa. Justifique."

Los renglones resaltados son los que lo delatan:

#include <iostream>
#include <string>

class Compresor {
 public:
  virtual ~Compresor() {}
  virtual std::string doAlgorithm(const std::string& nombre) const = 0;
};

class CompresorZip : public Compresor {
 public:
  std::string doAlgorithm(const std::string& nombre) const override {
    return nombre + ".zip";
  }
};

class CompresorRar : public Compresor {
 public:
  std::string doAlgorithm(const std::string& nombre) const override {
    return nombre + ".rar";
  }
};

class Archivador {
 private:
  Compresor* compresor_;

 public:
  Archivador(Compresor* compresor = nullptr) : compresor_(compresor) {}
  void set_compresor(Compresor* compresor) {
    this->compresor_ = compresor;
  }
  void doSomeBusinessLogic(const std::string& nombre) const {
    std::cout << "Archivador: genero " << this->compresor_->doAlgorithm(nombre) << "\n";
  }
};

int main() {
  CompresorZip zip;
  CompresorRar rar;
  Archivador archivador(&zip);
  archivador.doSomeBusinessLogic("informe");
  archivador.set_compresor(&rar);
  archivador.doSomeBusinessLogic("informe");
  return 0;
}
Archivador: genero informe.zip
Archivador: genero informe.rar
RenglónLo que se veQué parte del patrón es

10Clases que hacen la misma tarea de otra forma (también CompresorRar).Las Estrategias Concretas
26Guarda un puntero a la interfaz (no una lista).La estrategia actual, en el Contexto (Archivador)

Respuesta, en las mismas tres partes de siempre:

  1. Qué patrón y por qué: "Es Strategy, un patrón de comportamiento que se usa cuando hay varias formas de hacer una misma tarea y se quiere poder cambiar de una a otra mientras el programa corre. Se reconoce porque Archivador guarda un solo puntero a una interfaz (Compresor), tiene un método para cambiarlo y le pasa el trabajo."
  2. Cómo está aplicado: "Compresor es la estrategia (la interfaz común a todas las formas de hacer la tarea), con doAlgorithm(). CompresorZip y CompresorRar son las estrategias concretas (cada forma de hacerla). Archivador es el contexto (la clase que usa una estrategia y le delega la tarea): guarda una, la deja cambiar con set_compresor() y en doSomeBusinessLogic() le pasa el trabajo."
  3. Qué se gana: "El mismo archivador genera un .zip o un .rar según la estrategia que tenga puesta, y una forma nueva es una clase más, sin modificar Archivador."
No es Observer

Los dos guardan punteros a una interfaz. Strategy guarda uno y lo puede cambiar; Observer guarda muchos (una lista) y les avisa a todos.

Ejemplo 6 — Con formato de parcial: agregarlo a un diagrama

Inventado · con la forma de la Guía N°1, ejercicio 1

"Dado el siguiente diagrama de un sistema de sueldos: la clase Empleado tiene un método por cada forma de calcular el sueldo, y calcularSueldo() elige cuál usar según el atributo modalidad. Se van a sumar formas nuevas (por proyecto, por guardia) y un empleado puede cambiar de modalidad durante el año. Modifique el diagrama aplicando el patrón de diseño que corresponda. Justifique."

Qué hay en el diagrama. Los tres métodos sueldo...() son tres formas de hacer la misma tarea, metidas en la misma clase. El atributo modalidad es un texto que solo sirve para elegir entre ellas con un if. Cada forma nueva obliga a modificar Empleado.

Qué se cambia, en orden:

  1. Crear la interfaz Estrategia. CalculoDeSueldo, con un solo método: calcular(e: Empleado): double.
  2. Sacar cada forma a su propia clase. sueldoMensual(), sueldoPorHora() y sueldoPorComision() salen de Empleado y pasan a ser las clases SueldoMensual, SueldoPorHora y SueldoPorComision, que cumplen la interfaz.
  3. Cambiar el atributo del contexto. En Empleado, modalidad: string se reemplaza por calculo: CalculoDeSueldo, y se agrega cambiarCalculo(c: CalculoDeSueldo).
  4. Dejar el método principal. calcularSueldo() se queda en Empleado; ahora le pasa el trabajo a calculo.
  5. Dibujar el rombo. De Empleado a la interfaz CalculoDeSueldo.

El diagrama modificado:

Justificación: "Se aplica Strategy porque hay varias formas de hacer una misma tarea (calcular el sueldo) y se quiere poder cambiar de una a otra mientras el sistema funciona. Cada forma va en su propia clase, una estrategia concreta (SueldoMensual, SueldoPorHora y SueldoPorComision), y todas cumplen la misma interfaz, la estrategia (CalculoDeSueldo). Empleado es el contexto (la clase que usa una estrategia y le delega la tarea): guarda una y le pasa el cálculo. Así se agregan formas nuevas sin modificar Empleado."

A tener en cuenta al modificar el diagrama
  • El contexto guarda una sola estrategia: el rombo no lleva *. Si guardara muchas y les avisara, sería Observer.
  • calcularSueldo() no se borra: el cliente (Liquidacion) lo sigue llamando igual que antes.
  • El rombo va a la interfaz, no a las estrategias concretas.
  • El método de la interfaz se llama igual en todas las estrategias, aunque antes tuvieran nombres distintos.

Ejemplo 7 — Con formato de guía: reconocerlo en un diagrama

El ejercicio 4 de Patrones de Diseño Parte 2 da este diagrama y pregunta qué patrón es:

Un Coche con un rombo hacia la interfaz IComportamientoFrenos, que tiene debajo FrenadoNormal y FrenadoABS. Es Strategy: el coche (contexto) tiene un comportamiento de frenos (estrategia) intercambiable. Está resuelto en la Práctica, ejercicio 5.

Errores y trampas

El contexto no elige

Si la clase tiene un if que decide "si es en auto, hago esto; si es a pie, esto otro", no hay patrón: es el problema original. En Strategy la estrategia llega desde afuera y el contexto solo la usa.

Con qué se confunde
  • Con Factory Method: los dos tienen una interfaz con variantes. Factory Method resuelve qué objeto se crea (hay un método que devuelve un new); Strategy resuelve cómo se hace una tarea (hay un método que hace el trabajo, y nadie crea nada).
  • Con Observer: en el diagrama, una lista con * y métodos de suscripción es Observer; una sola referencia y un método para cambiarla es Strategy.
