4. Git: los comandos, del directorio de trabajo al remoto

Unidad 6 · Git

Un equipo tiene como rama principal a master, que es la versión estable. Un desarrollador, que está ubicado en master, tiene que programar el inicio de sesión en una rama nueva llamada feature-login. Indique los pasos que debe seguir para crear esa rama, registrar en ella todos los cambios del Working Directory, subirla al remoto, integrarla en master y dejar master actualizada en el remoto (Git Workflow).

✓ RespuestaPara aprender y escribir en la hoja
  1. Crear la rama y pasarse a ella: git checkout -b feature-login
  2. Preparar todos los cambios: git add .
  3. Confirmarlos: git commit -m "Agrega el inicio de sesión"
  4. Subir la rama al remoto: git push origin feature-login
  5. Volver a la rama principal: git checkout master
  6. Integrar la rama: git merge feature-login
  7. Subir master al remoto: git push origin master
✎ Explicación desde ceroParte por parte

El mapa

Cada comando de Git mueve los cambios de un lugar a otro:

Directorio        Área de          Repositorio         Repositorio
de trabajo        preparación      local               remoto (origin)

    │── git add ──────▶│                │                    │
    │                  │── git commit ─▶│                    │
    │                  │                │──── git push ─────▶│

Una rama es una versión paralela del proyecto: permite trabajar en algo nuevo sin afectar la rama principal. origin es el nombre que Git le pone por defecto al remoto.

Cada comando: qué hace y por qué va ahí
ComandoQué hacePor qué va en ese lugar
git checkout -b feature-loginCrea la rama nueva y cambia a ella.Va primero para que los commits caigan en la rama nueva y no en master.
git add .Prepara todos los cambios (el punto es "todo lo de esta carpeta").El commit guarda solo lo que está en el área de preparación.
git commit -m "..."Confirma lo preparado en feature-login, con un mensaje.Sin commit no hay nada para subir: el push sube commits.
git push origin feature-loginSube la rama al remoto.Hasta acá la rama existía solo en el repositorio local.
git checkout masterCambia a master, que todavía no tiene los cambios.El merge trae los cambios a la rama en la que estoy parado.
git merge feature-loginTrae a master lo que tiene feature-login.Recién ahora master tiene el inicio de sesión, pero solo en local.
git push origin masterSube master al remoto.Es lo último: deja el remoto actualizado.
Por qué el merge se hace parado en la rama que recibe

git merge rama no lleva un "destino": siempre trae los cambios de la rama que se nombra hacia la rama actual. Para que reciba master hay que estar en master. Si te quedás en feature-login y escribís git merge master, hacés lo contrario: traés master a tu rama, y master queda sin el inicio de sesión.

Trampas

  • Dos push, uno por rama: git push origin master sube solo master. Si la consigna pide subir la rama nueva, lleva su propio push.
  • checkout -b crea; checkout solo cambia: sin el -b, la rama tiene que existir.
  • Sin add no hay commit: saltearlo es saltearse un estado.
  • Suma agregar git pull origin master antes de crear la rama y antes del merge, para traer lo que hayan subido los demás.
