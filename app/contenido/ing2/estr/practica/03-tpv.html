Ejercicio 3 · Adapter

Diseñar desde un enunciado: el terminal de punto de venta

Guía N°1, ejercicio 3. Una empresa que desarrolla sistemas software de terminal de punto de venta, TPV solicita que se diseñe un diagrama de clases implementando patrones de diseño. Estos sistemas deben permitir la conexión a ordenadores remotos para procesar los pagos por tarjeta de crédito. Cada comercio podrá utilizar diferentes servicios externos de autorización de pago para distintos tipos de tarjeta (uno para VISA, otro para MasterCard, etc.) cada uno de los cuales tiene su propia API. El tipo de compañía de crédito se puede deducir del código de la tarjeta (si empieza por 5 es una MasterCard, por 4 una VISA, etc.). Cada comercio tiene un identificador dependiendo del tipo de tarjeta que debe enviarse con la solicitud de pago.

a) Diseña una solución para que el sistema TPV pueda interactuar con diferentes sistemas externos de autorización de pago utilizando patrones de diseño.
b) ¿Qué patrón utilizaste? ¿Qué ventaja tiene?

Paso 1 — Desarme del enunciado

API es la forma en que se usa un servicio: qué métodos tiene y qué datos pide. "Cada uno tiene su propia API" quiere decir cada uno tiene una interfaz distinta.

Frase del enunciadoQué significaParte del patrón
"el sistema TPV pueda interactuar con..."El sistema propio, que quiere cobrar siempre de la misma formaCliente: TPV
"diferentes servicios externos de autorización de pago (uno para VISA, otro para MasterCard, etc.)"Clases de terceros, que no se pueden modificarServicios: ServicioVisa, ServicioMasterCard
"cada uno de los cuales tiene su propia API"Interfaces distintas entre sí, e incompatibles con la del TPV. La frase que decide.Hace falta un Adaptador por servicio
"el tipo de compañía se puede deducir del código de la tarjeta"El TPV sabe qué adaptador usar mirando el primer dígitoLa elección del adaptador
"cada comercio tiene un identificador (...) que debe enviarse con la solicitud"Un dato más que hay que pasarle al servicioUn parámetro del método común
Paso 2 — La solución
  1. Se define una interfaz propia, AutorizadorPago, con el método que el TPV necesita: autorizar(tarjeta, importe, idComercio).
  2. Por cada servicio externo se escribe un adaptador que cumple esa interfaz, guarda al servicio y traduce la llamada a la API propia de ese servicio.
  3. El TPV mira el código de la tarjeta, elige el adaptador que corresponde y le pide autorizar(...), igual para todos.
Paso 3 — El diagrama
Respuesta

a) El diagrama de arriba.
b) Patrón Adapter: cada servicio externo de autorización tiene su propia API, incompatible con la del TPV. Se define la interfaz AutorizadorPago y un adaptador por servicio, que la implementa y traduce las llamadas. Ventaja: el TPV trabaja con todos de la misma forma, sin depender de la API de cada compañía; y para sumar una tarjeta nueva alcanza con agregar un adaptador, sin modificar el TPV ni los servicios (principio de abierto/cerrado).

Por qué no Facade ni Factory Method
  • Facade simplificaría varios servicios que se usan juntos para una misma operación. Acá se usa uno u otro, y el problema es que cada uno "habla distinto".
  • Factory Method se podría sumar para decidir qué adaptador crear según el código de la tarjeta, pero no resuelve lo que pregunta el enunciado, que es cómo interactuar con sistemas de API distinta.
