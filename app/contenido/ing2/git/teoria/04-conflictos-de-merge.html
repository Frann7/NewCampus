Git

4. Conflictos de merge

Para qué sirve

Cuando se fusionan dos ramas, Git intenta combinar los cambios solo. Si en cada rama se tocaron partes distintas, lo logra: el merge es automático. Si las dos ramas cambiaron las mismas líneas del mismo archivo, Git no puede adivinar cuál vale: se detiene y le pide a una persona que decida. Eso es un conflicto de merge.

Tipos de conflicto

TipoCuándo ocurre
De contenido (en el mismo archivo)Las dos ramas modificaron la misma línea de un archivo.
De eliminaciónUna rama eliminó un archivo que la otra rama modificó.

Cómo se ve un conflicto

Git marca dentro del archivo las dos versiones, con tres líneas de señales:

<<<<<<< HEAD
Cambios en la rama actual
=======
Cambios en la rama "feature-nueva-funcion"
>>>>>>> feature-nueva-funcion
ParteQué es
<<<<<<< HEADEmpieza la versión de la rama actual (en la que estoy parado). HEAD es "donde estoy".
=======La separación entre las dos versiones.
>>>>>>> nombre-de-la-ramaTermina la versión de la otra rama, la que se está fusionando.

Cómo se resuelve: cuatro pasos

#PasoComando
1Ver qué archivos están en conflicto.git status
2Editar a mano cada archivo: elegir una versión, o combinar las dos, y borrar las tres líneas de señales.(en el editor)
3Marcar el conflicto como resuelto, agregando el archivo al área de preparación.git add nombre_archivo
4Finalizar el merge con un commit.git commit

Dos comandos útiles más:

  • git merge --abort: descarta el merge y deja la rama como estaba antes de intentarlo.
  • git mergetool: abre una herramienta visual para resolver los conflictos, si hay alguna configurada.

Ejemplo 1 — Un conflicto real, de principio a fin

El título de index.html se cambió de dos formas distintas: en main quedó "Hola, bienvenidos" y en la rama feature-nueva-funcion, "Bienvenidos a la tienda". Parado en main: 

git merge feature-nueva-funcion
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

Git avisa que el merge automático falló y qué hay que hacer: arreglar los conflictos y después confirmar. Paso 1, ver qué archivos están en conflicto: 

git status --short
UU index.html

UU quiere decir "modificado en las dos ramas, sin fusionar". Paso 2, abrir el archivo:

<<<<<<< HEAD
<h1>Hola, bienvenidos</h1>
=======
<h1>Bienvenidos a la tienda</h1>
>>>>>>> feature-nueva-funcion
  • Arriba, lo de HEAD: la versión de main.
  • Abajo, la versión de feature-nueva-funcion.

Se decide combinar las dos. El archivo se deja así, sin las señales:

<h1>Hola, bienvenidos a la tienda</h1>

Pasos 3 y 4, marcar como resuelto y finalizar:

git add index.html
git commit -m "Resuelve el conflicto del titulo"

El historial (git log --oneline --graph) muestra las dos ramas que se abrieron y se volvieron a unir:

*   aaf0999 Resuelve el conflicto del titulo
|\
| * b4a342c Titulo de la tienda
* | 478cb40 Saludo en el titulo
|/
* c11a3b1 Cambia el titulo y agrega estilos

Se lee de abajo hacia arriba: desde un commit común salieron dos caminos, uno por cada rama, y el commit de arriba es el merge que los junta.

Ejemplo 2 — Con formato de parcial: los pasos para resolver un conflicto

"Al hacer un merge, Git informa un conflicto. Indique los pasos para resolverlo."

Respuesta: "1) Con git status se ven los archivos en conflicto. 2) Se abre cada archivo y se editan las partes marcadas con <<<<<<<, ======= y >>>>>>>, eligiendo qué versión conservar o combinando ambas, y se borran las marcas. 3) Se marca como resuelto con git add archivo. 4) Se finaliza el merge con git commit. Si se quiere cancelar, git merge --abort vuelve la rama a su estado anterior."

El apunte lo resume casi con las mismas palabras, en su "resumen para una clase".

Errores y trampas

Las señales no se borran solas

Hacer git add sin editar el archivo deja las líneas <<<<<<< y ======= adentro del código, y quedan confirmadas así. Git no revisa que las hayas sacado.

Un conflicto no es un error

Es Git negándose a elegir por vos. Es normal cuando dos personas tocan lo mismo, y por eso el control de versiones es mejor que no tenerlo: sin él, el último que guarda pisa al otro sin que nadie se entere.

No toda fusión da conflicto

Si las dos ramas tocaron archivos distintos, o líneas distintas del mismo archivo, el merge es automático. El conflicto aparece solo cuando se superponen.
