Ejemplo de la cátedra · ataqueForm

Un formulario sin protección y el script que lo ataca

Carpeta ataqueForm: formulario.html pide usuario y contraseña y los manda a procesoForm.php, que los muestra. ataque.php manda esos mismos datos diez veces sin pasar por el formulario.

Archivo 1 — formulario.html 
<form method="post" action="procesoForm.php">
    <div class="form-row">
        <div class="col-md-6 mb-3">
            <label for="nombre">Usuario</label>
            <input type="text" class="form-control" name="usuario" value="" required>
        </div>
        <div class="col-md-6 mb-3">
            <label for="contrasenia">Contraseña:</label>
            <input type="password" class="form-control" name="contrasenia" value="">
        </div>
    </div>
    <button class="btn btn-primary" type="submit">Enviar datos</button>
</form>

Es un archivo .html puro (no tiene PHP). Arriba lleva el encabezado con Bootstrap y el título "Sistema Recursos Humanos"; acá va solo el formulario, que es lo que importa.

LíneaQué hace
<form method="post" action="procesoForm.php">Al enviar, manda los campos por POST a procesoForm.php (Clase 3).
name="usuario" ... requiredCampo de texto; required hace que el navegador no deje enviar si está vacío.
type="password" name="contrasenia"Campo de contraseña: muestra puntitos en vez de letras.
class="form-row", col-md-6, btn btn-primary...Clases de Bootstrap: solo dan el diseño (dos columnas, botón azul).
<button type="submit">El botón que envía.
Archivo 2 — procesoForm.php 
<?php
if (!empty($_POST)) {
    echo "USUARIO: " . $_POST['usuario'];
    echo "==>";
    echo "CONTRASEÑA: " . $_POST['contrasenia'];
    echo "<br>";
}
?>
LíneaQué hace
if (!empty($_POST))Solo hace algo si llegó un POST con datos. Abierto directo desde la barra de direcciones (GET), no muestra nada.
los cuatro echoMuestran lo que llegó, sin preguntar de dónde vino. Acá está el problema: no hay ningún control.

Enviando el formulario a mano con usuario fran y contraseña 1234, responde:

USUARIO: fran==>CONTRASEÑA: 1234
Archivo 3 — ataque.php 
<?php
$url = "http://localhost/clase5/ataqueForm/procesoForm.php";

for ($i = 1; $i <= 10; $i++) {
    $usuario = 'Federico';
    $contrasenia = 'Bonnet';

    $fields = ['usuario' => $usuario, 'contrasenia' => $contrasenia];

    $campos_string = http_build_query($fields);

    $ch = curl_init();
        curl_setopt($ch, CURLOPT_URL, $url);
        curl_setopt($ch, CURLOPT_POST, true);
        curl_setopt($ch, CURLOPT_POSTFIELDS, $campos_string);
        curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
    $result = curl_exec($ch);

    print_r($result);

    curl_close($ch);
}
?>

Qué problema de seguridad muestra
  • procesoForm.php no puede distinguir un envío real de uno armado por un programa: los dos le llegan como un POST con usuario y contrasenia.
  • El required del formulario no sirvió de nada: cURL no pasa por el HTML.
  • Si procesoForm.php guardara en una base de datos, serían 10 registros falsos; con un for más largo, millones. O, con un login, alguien podría probar miles de contraseñas por minuto.
  • La defensa está en los dos ejemplos siguientes: el token y el captcha.
Detalles del ejemplo
  • En el formulario, <label for="nombre"> no coincide con ningún campo (el for se empareja con un id, y los input no tienen): solo hace que tocar el rótulo no lleve el cursor al campo. No afecta el envío.
  • ataque.php corre en el mismo XAMPP, así que su $url es localhost. Un atacante real pondría la dirección de tu sitio y lo correría desde su máquina.
