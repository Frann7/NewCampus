1. Adapter

También llamado Adaptador, Envoltorio o Wrapper.

Para qué sirve

Tenés un programa que funciona y querés sumarle una clase que ya existe (una biblioteca de otro, un sistema viejo, un servicio externo). Hace lo que necesitás, pero se usa de otra manera: sus métodos se llaman distinto, o piden los datos en otro formato. Su interfaz es incompatible con la que espera tu código.

  • Cambiar tu programa para adaptarlo a ella obliga a tocar todo lo que ya funciona.
  • Cambiar la clase ajena muchas veces es imposible: no es tuya o ni tenés su código.

El Adapter es una clase intermedia que hace de traductor: por fuera se ve como lo que tu programa espera, y por dentro le pasa el pedido a la clase ajena, convirtiendo lo que haga falta.

Analogía del apunte: el adaptador de enchufes. El enchufe de la notebook no entra en el tomacorriente de otro país; no se cambia ni la notebook ni la pared, se pone un adaptador en el medio.

Propósito

Adapter es un patrón estructural que permite la colaboración entre objetos con interfaces incompatibles.

Estructura

ParteQué esEn el ejemplo del termómetro
ClienteEl código que ya existe y funciona.La función mostrar()
Interfaz con el Cliente (Target)La interfaz que el cliente espera: lo que sabe usar.Termometro, con celsius()
Servicio (Adaptee)La clase útil pero incompatible. No se modifica, y ni se entera de que existe un adaptador.SensorAmericano, con leerFahrenheit()
Adaptador (Adapter)Cumple la interfaz del cliente y guarda un objeto del servicio. Cuando el cliente lo llama, traduce el pedido y se lo pasa al servicio.AdaptadorSensor

Cómo dibujarlo de memoria: el adaptador tiene dos flechas.

  • Una punteada con triángulo hacia arriba: cumple la interfaz que el cliente conoce.
  • Una continua hacia el costado: guarda al servicio (por eso tiene un atributo de ese tipo).
  • El Cliente apunta a la interfaz, nunca al Adaptador ni al Servicio.

El apunte lo llama adaptador de objetos, porque el adaptador contiene al servicio. Existe otra versión, la clase adaptadora, en la que el adaptador hereda a la vez de la interfaz del cliente y del servicio; solo se puede hacer en lenguajes con herencia múltiple, como C++. La que se usa y se dibuja normalmente es la primera.

Ejemplo 1 — En C++: un sensor que mide en otra unidad

El programa trabaja con termómetros que dan la temperatura en grados Celsius. Se compra un sensor de otro fabricante que la da en Fahrenheit y con otro nombre de método.

El programa, en 6 partes. Los números de la izquierda son los renglones del programa completo; los renglones resaltados son los que hay que mirar.

1Las bibliotecas

#include <iostream>
#include <string>

2Lo que el programa sabe usarInterfaz con el cliente

class Termometro {
 public:
  virtual ~Termometro() {}
  virtual double celsius() const = 0;
};

class TermometroDigital : public Termometro {
 public:
  double celsius() const override {
    return 21.5;
  }
};

Termometro tiene celsius(). TermometroDigital es un termómetro propio, que ya encajaba; está para comparar.

3La clase ajenaServicio

class SensorAmericano {
 public:
  double leerFahrenheit() const {
    return 77.0;
  }
};

No hereda de Termometro, su método se llama distinto y devuelve otra unidad. No se la toca.

4El traductorAdaptador

class AdaptadorSensor : public Termometro {
 private:
  SensorAmericano* sensor_;

 public:
  AdaptadorSensor(SensorAmericano* sensor) : sensor_(sensor) {}

  double celsius() const override {
    return (sensor_->leerFahrenheit() - 32) * 5 / 9;
  }
};

Sus dos flechas: hereda de Termometro y guarda un puntero al sensor. En celsius() le pide el dato al sensor y lo convierte.

5El código que ya existíaCliente

void mostrar(Termometro* t) {
  std::cout << "Temperatura: " << t->celsius() << " grados\n";
}

Solo conoce Termometro.

6El programa

int main() {
  Termometro* propio = new TermometroDigital;
  mostrar(propio);

  SensorAmericano* sensor = new SensorAmericano;
  Termometro* adaptado = new AdaptadorSensor(sensor);
  mostrar(adaptado);

  delete propio;
  delete adaptado;
  delete sensor;
  return 0;
}

Primero con un termómetro propio; después con el sensor ajeno, envuelto en el adaptador.

Cómo reconocerlo

DóndeQué lo delata
En un enunciado"interfaces incompatibles", "se debe adaptar la nueva clase sin que afecte la lógica de la aplicación", "con un funcionamiento diferente al que se está manejando", "servicios externos (...) cada uno de los cuales tiene su propia API", "bibliotecas externas (...) con una interfaz diferente e incompatible".
En un código
  1. una clase suelta, que no hereda de nada, con un método de nombre "raro" (SpecificRequest): el servicio;
  2. otra clase que hereda de la interfaz que usa el cliente y guarda un puntero al servicio, recibido en el constructor: el adaptador;
  3. en el adaptador, el método de la interfaz llama al método del servicio y transforma el resultado antes de devolverlo.

Ventajas y desventajas

VentajasDesventajas
  • Principio de responsabilidad única: el código de conversión queda separado de la lógica principal del programa.
  • Principio de abierto/cerrado: se pueden agregar adaptadores nuevos sin romper el código cliente, que trabaja con ellos a través de la interfaz.
  • La complejidad general aumenta: hay que sumar interfaces y clases. A veces es más simple cambiar directamente la clase de servicio para que coincida con el resto.

Dónde se usa

  • Para usar una clase existente cuya interfaz no es compatible con el resto del código: una clase heredada, de un tercero o "con una interfaz extraña".
  • El ejemplo del apunte: una aplicación de bolsa que trabaja con datos en XML y quiere usar una biblioteca de análisis que solo acepta JSON.
  • Pasarelas de pago: cada tarjeta tiene su servicio con su propia API, y el sistema quiere cobrar siempre igual.

Parcial 2025 · Teoría 4 (20 puntos, con Abstract Factory)

"... planea incorporar dos patrones de diseño en su solución empresarial, la creación flexible de familias de objetos y otro para conectar módulos con interfaces incompatibles con los existentes del sistema."

El diagrama: Cliente, Interfaz con el Cliente, Adaptador y Servicio, con las dos flechas del adaptador.

  • Un sistema de cobros que suma un proveedor nuevo. "El sistema cobra a través de su interfaz MedioDePago y el proveedor trae otros métodos. El adaptador cumple MedioDePago y por dentro llama al proveedor, sin tocar ninguno de los dos."

Ejemplo 4 — Con formato de parcial: reconocerlo en un código

Con la forma del Parcial 2024 · ejercicio 4

"A partir del siguiente código identifique qué patrón es el que se utiliza. Justifique."

Los renglones resaltados son los que lo delatan:

#include <algorithm>
#include <iostream>
#include <string>

class Reproductor {
 public:
  virtual ~Reproductor() = default;
  virtual std::string Request() const {
    return "Reproductor: sonido estandar.";
  }
};

class CasetteraVieja {
 public:
  std::string SpecificRequest() const {
    return "ajeiv arettesac al ed odinoS";
  }
};

class Acople : public Reproductor {
 private:
  CasetteraVieja* adaptee_;

 public:
  Acople(CasetteraVieja* adaptee) : adaptee_(adaptee) {}
  std::string Request() const override {
    std::string al_reves = this->adaptee_->SpecificRequest();
    std::reverse(al_reves.begin(), al_reves.end());
    return "Acople: (TRADUCIDO) " + al_reves;
  }
};

void ClientCode(const Reproductor* reproductor) {
  std::cout << reproductor->Request() << "\n";
}

int main() {
  Reproductor* reproductor = new Reproductor;
  ClientCode(reproductor);
  CasetteraVieja* casettera = new CasetteraVieja;
  Acople* acople = new Acople(casettera);
  ClientCode(acople);
  delete reproductor;
  delete casettera;
  delete acople;
  return 0;
}
Reproductor: sonido estandar.
Acople: (TRADUCIDO) Sonido de la casettera vieja
RenglónLo que se veQué parte del patrón es
5La clase que el cliente ya sabe usar, con el método Request().La Interfaz con el Cliente (Target)
13Una clase útil pero con otro método, SpecificRequest(), que no hereda de nadie.El Servicio (Adaptee)
20Hereda de la clase que espera el cliente.El Adaptador
22Guarda un objeto de la clase incompatible.La referencia del adaptador al Servicio
27En Request() llama al método del servicio y convierte lo que devuelve.La traducción
42El cliente recibe el adaptador como si fuera un Reproductor.El Cliente, que no se entera

Respuesta: "Es el patrón Adapter (estructural). El cliente trabaja con Reproductor y su método Request(). CasetteraVieja tiene una interfaz incompatible (SpecificRequest(), que además devuelve el texto al revés). Acople es el adaptador: hereda de Reproductor, guarda una CasetteraVieja y en Request() llama a SpecificRequest() y traduce el resultado. El cliente lo usa sin saber que detrás hay otra clase."

No es Facade

Los dos envuelven, pero acá se envuelve una clase para que cumpla una interfaz que ya existía (Reproductor). En Facade la clase nueva guarda varias y no hereda de nadie: inventa una interfaz más simple.

Ejemplo 5 — Con formato de parcial: agregarlo a un diagrama

Con la forma del Parcial 2024 · ejercicio 3

"Dado el siguiente diagrama: el Tablero muestra gráficos a través de la interfaz Grafico. Se compró la librería MapaExterno y se quiere mostrar el mapa en el tablero junto con los demás gráficos. No se puede modificar la librería ni la clase Tablero. Modifique el diagrama aplicando el patrón de diseño que corresponda. Justifique."

Qué hay en el diagrama. Tres de las cuatro partes del patrón ya están dibujadas: el Cliente (Tablero), la Interfaz con el Cliente (Grafico) y el Servicio (MapaExterno, que está suelto, sin ninguna línea). El método del servicio se llama distinto y recibe otros datos: renderizar(json, zoom) contra dibujar(datos).

Qué se cambia, en orden:

  1. Agregar una sola clase: el Adaptador. AdaptadorDeMapa, al lado de los otros gráficos.
  2. Hacer que cumpla la interfaz. Línea punteada con triángulo hacia Grafico, y el mismo método dibujar(datos).
  3. Hacer que guarde al servicio. El atributo - mapa: MapaExterno y una flecha de asociación hacia MapaExterno.

El diagrama modificado:

Justificación: "Se aplica Adapter porque MapaExterno tiene una interfaz incompatible con Grafico y no se puede modificar. AdaptadorDeMapa implementa Grafico y guarda un MapaExterno: cuando el tablero le pide dibujar(datos), convierte los datos y llama a renderizar(json, zoom). El Tablero lo trata como a un gráfico más."

A tener en cuenta al modificar el diagrama
  • El adaptador es la única caja nueva. Ni Tablero, ni Grafico, ni MapaExterno cambian.
  • El error típico: unir MapaExterno con Grafico con una línea de realización. Eso es modificar la librería, que es lo que el enunciado prohíbe.
  • El adaptador lleva dos líneas: una punteada con triángulo (cumple la interfaz) y una de asociación (guarda al servicio).
  • La cátedra tiene su propio enunciado de esta forma, el del libro digital, que está en tres guías: Práctica, ejercicio 2.

Errores y trampas

El servicio no se toca

Si la solución modifica la clase nueva o la hace heredar de la interfaz, no hay patrón. La gracia del Adapter es que ni el cliente ni el servicio cambian.

Con qué se confunde

Con Facade: los dos ponen una clase en el medio. El Adapter envuelve una clase para darle una interfaz que ya existía (la que espera el cliente). La Facade envuelve varias y define una interfaz nueva, más simple.
