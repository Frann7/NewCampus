Creacional

2. Factory Method

También llamado Método Fábrica.

Para qué sirve

El problema, con el ejemplo del apunte:

  • Una aplicación de logística nació manejando solo camiones. Por eso el código está lleno de new Camion: está acoplado (atado) a la clase Camion.
  • Ahora piden agregar barcos. Hay que tocar todos los lugares donde se creaba un camión y llenarlos de condicionales: "si es por tierra, camión; si es por mar, barco".
  • Cuando mañana pidan aviones, hay que volver a tocar todo.

Factory Method saca el new del medio del código y lo pone en un método aparte, el método fábrica. La clase base lo llama cuando necesita el objeto, pero son las subclases las que deciden qué objeto concreto devuelve.

Propósito

Factory Method es un patrón creacional que proporciona una interfaz para crear objetos en una superclase, mientras permite a las subclases alterar el tipo de objetos que se crearán.

La idea de la solución

  1. Todos los objetos que se pueden crear (Camion, Barco) cumplen una misma interfaz (Transporte). A esos objetos se los llama productos.
  2. La clase que los necesita (Logistica) no hace new: llama a su método fábrica crearTransporte(), que devuelve "un Transporte", sin decir cuál.
  3. Cada subclase (LogisticaTerrestre, LogisticaMaritima) escribe ese método a su manera: una devuelve un camión, la otra un barco.

Resultado: para agregar aviones se crean dos clases nuevas (Avion y LogisticaAerea) y no se toca nada de lo que ya estaba.

Cómo dibujarlo de memoria: dos familias en paralelo.

  • A la izquierda, la de los creadores: uno abstracto arriba y los concretos abajo.
  • A la derecha, la de los productos: la interfaz arriba y los concretos abajo.
  • Una flecha punteada "crea" del Creador al Producto.
  • Va un creador concreto por cada producto concreto. En los creadores concretos el método se repite (lo sobrescriben); alcanza con poner el tipo que devuelve una sola vez, en el de arriba.
El Producto: interfaz en la estructura general, clase abstracta si hay atributos

El apunte dibuja el Producto como interfaz, y así va cuando piden la estructura del patrón. Pero también admite que sea una clase: dice que los productos tienen que tener "una clase base o interfaz común". Cuál de las dos va lo decide el enunciado:

El enunciado dice que los productos...El Producto esLos Productos Concretos llegan con
Solo comparten métodosUna interfaz («interface»)Línea punteada con triángulo (realización)
Comparten también atributosUna clase abstracta («abstract»)Línea continua con triángulo (herencia)

Una interfaz no puede tener atributos: por eso, si el enunciado da datos que tienen todos los productos, esos datos tienen que ir en una clase. El patrón es Factory Method en los dos casos: lo que lo define es el Creador con su método fábrica, no la forma del Producto.

Ejemplo 1 — En C++: la logística del apunte

El programa, en 6 partes. Los números de la izquierda son los renglones del programa completo; los renglones resaltados son los que hay que mirar.

1Las bibliotecas

#include <iostream>
#include <string>

2La interfaz de lo que se creaProducto

class Transporte {
 public:
  virtual ~Transporte() {}
  virtual std::string entregar() const = 0;
};

Todo transporte sabe entregar().

3Los transportes que existenProductos concretos

class Camion : public Transporte {
 public:
  std::string entregar() const override {
    return "entrega por tierra, en un camion";
  }
};

class Barco : public Transporte {
 public:
  std::string entregar() const override {
    return "entrega por mar, en un barco";
  }
};

Cada uno entrega a su manera.

4La clase que necesita un transporteCreador

class Logistica {
 public:
  virtual ~Logistica() {}
  virtual Transporte* crearTransporte() const = 0;

  std::string planificarEntrega() const {
    Transporte* t = crearTransporte();
    std::string resultado = "Logistica: " + t->entregar();
    delete t;
    return resultado;
  }
};

crearTransporte() es el método fábrica: devuelve "un Transporte" y no tiene código. planificarEntrega() lo llama donde antes habría un new Camion.

5Quién decide qué se creaCreadores concretos

class LogisticaTerrestre : public Logistica {
 public:
  Transporte* crearTransporte() const override {
    return new Camion;
  }
};

class LogisticaMaritima : public Logistica {
 public:
  Transporte* crearTransporte() const override {
    return new Barco;
  }
};

Acá sí está el new: cada subclase escribe el método fábrica y elige el transporte.

6El programa

int main() {
  Logistica* l = new LogisticaTerrestre;
  std::cout << l->planificarEntrega() << "\n";
  delete l;

  l = new LogisticaMaritima;
  std::cout << l->planificarEntrega() << "\n";
  delete l;
  return 0;
}

La misma llamada, planificarEntrega(), sobre las dos logísticas.

Cómo reconocerlo

DóndeQué lo delata
En un enunciadoSe habla de crear objetos de distintos tipos de una misma cosa, y de que el resto no tenga que saber cuál: "crear instancias de estos enemigos de manera dinámica", "poder agregar nuevos tipos de archivo en el futuro", "trabajar con diferentes bases de datos de manera transparente", "un problema que tiene que ver con la creación de los objetos".
En un código
  1. una clase base con un método virtual (muchas veces = 0) que devuelve un puntero a otra clase base: ese es el método fábrica (FactoryMethod, crear..., create...);
  2. subclases cuyo override de ese método es apenas un return new Algo;;
  3. en la clase base, otro método que llama al método fábrica y usa lo que le devuelven.

Ventajas y desventajas

VentajasDesventajas
  • Evita un acoplamiento fuerte entre el creador y los productos concretos.
  • Principio de responsabilidad única: el código que crea productos queda en un solo lugar, más fácil de mantener.
  • Principio de abierto/cerrado: se agregan tipos nuevos de productos sin romper el código que ya existe.
  • El código se puede complicar, porque hay que agregar muchas subclases nuevas (una creadora por cada producto).
Los dos principios que nombra el apunte en casi todos los patrones

Responsabilidad única: cada clase se ocupa de una sola cosa.
Abierto/cerrado: el código está abierto a agregarle cosas nuevas y cerrado a modificar lo que ya funciona. Se agrega una clase; no se edita una vieja.

Dónde se usa

  • Cuando no se sabe de antemano los tipos exactos de objetos con los que va a trabajar el código (camiones hoy, barcos mañana).
  • En una biblioteca o framework, para que quien lo usa pueda extender sus componentes: el framework crea "un botón" con un método fábrica y el usuario lo sobrescribe para que cree su botón redondo.
  • Para reutilizar objetos costosos (conexiones a bases de datos) en vez de crearlos cada vez: el método fábrica puede devolver uno que ya existía.

Ejemplo 3 — Con formato de parcial: aplicarlo a un enunciado

Ejercicios de patrones · ejercicio 3

"Estás desarrollando una aplicación que necesita conectarse a diferentes bases de datos, como MySQL, PostgreSQL y MongoDB. Cada base de datos tiene sus propias características y configuraciones. Necesitas implementar un sistema que permita crear objetos de conexión a la base de datos de manera que la aplicación pueda trabajar con diferentes bases de datos de manera transparente. Cada objeto de conexión tiene los siguientes atributos: nombre de la base de datos, host, puerto, usuario y contraseña."

La guía no trae consigna aparte: hay que decir qué patrón se aplica, justificarlo y dibujarlo.

Frase del enunciadoQué significaParte del patrón
"crear objetos de conexión"El problema es de creación: el patrón es creacionalEl método fábrica: crearConexion()
"diferentes bases de datos, como MySQL, PostgreSQL y MongoDB"Varios tipos de una misma cosa (una conexión)Producto: Conexion. Productos Concretos: ConexionMySQL, ConexionPostgreSQL, ConexionMongoDB
"Cada base de datos tiene sus propias características y configuraciones"Cada tipo se crea a su maneraUn Creador Concreto por cada base de datos
"trabajar con diferentes bases de datos de manera transparente"La aplicación no nombra las clases concretasLa aplicación usa Conexion y al Creador (CreadorDeConexiones)
"nombre de la base de datos, host, puerto, usuario y contraseña"Atributos que tienen todas las conexionesVan una sola vez, en Conexion, protegidos (#) para que los hereden las concretas

Acá el Producto es una clase abstracta, no una interfaz. El enunciado dice que toda conexión tiene cinco atributos, y una interfaz no puede tener atributos: van en Conexion, que pasa a ser una clase abstracta, y las conexiones concretas la heredan (línea continua). Es la única diferencia con el diagrama general del patrón, donde el Producto es una interfaz y la línea es punteada.

Justificación. Es la descripción del patrón (la del ejemplo 2) dicha con los nombres de este caso, en las mismas tres partes: cuándo se usa, cómo funciona y qué se gana.

  1. Qué patrón y por qué: "Se aplica Factory Method, un patrón creacional, porque la aplicación no puede saber de antemano qué tipo exacto de conexión tiene que crear: puede ser a MySQL, a PostgreSQL o a MongoDB. El enunciado lo dice: "crear objetos de conexión a la base de datos de manera que la aplicación pueda trabajar con diferentes bases de datos"."
  2. Cómo se aplica: "La creación se saca a un método, el método fábrica crearConexion(), que la clase base CreadorDeConexiones declara y cada subclase (CreadorMySQL, CreadorPostgreSQL, CreadorMongoDB) sobrescribe para devolver su conexión. Todas las conexiones tienen un tipo común, Conexion, que es el producto."
  3. Qué se gana: "Se agregan tipos nuevos sin modificar el código que los usa: otra base de datos (por ejemplo, SQLite) es una conexión y un creador más."

Por qué no es Abstract Factory: hay un solo tipo de producto (la conexión) en varias versiones, no varios productos que tengan que combinar.

Ejemplo 4 — Con formato de parcial: identificar los patrones de un enunciado

Inventado · con la forma del Parcial 2025, Práctica 1

"A partir del siguiente enunciado identifique cuáles serían los patrones de diseño que utilizaría y justifique por qué eligió los mismos."

"DocuPyme desarrolla un sistema de gestión de trámites para municipios. El sistema debe consultar el padrón de contribuyentes, que pertenece a la provincia y se accede mediante un servicio cuyas operaciones tienen nombres y formatos diferentes de los que utiliza el sistema municipal. Ese servicio no puede modificarse, y tampoco se desea reescribir los módulos que hoy consultan los datos de los vecinos."

"Cada trámite que inicia un vecino genera un documento, que puede ser una solicitud, un reclamo o una habilitación. Para cada tipo de documento existe una oficina con su propio procedimiento para generarlo, de modo que la mesa de entradas no necesita conocer cómo se arma cada uno. El municipio ya anunció que incorporará nuevos tipos de documento, y se espera poder sumarlos sin modificar la mesa de entradas."

"Por razones de seguridad, todo acceso al sistema debe pasar por un control de sesiones. Se requiere que exista un único gestor de sesiones para toda la aplicación, de manera que no puedan crearse otros."

El enunciado mezcla Factory Method con otros dos patrones, como en el parcial. El método: un párrafo, una necesidad, un patrón. En cada párrafo se busca qué se necesita y la frase que lo dice.

PárrafoLa necesidadLa frase que lo delataPatrón
1. El padrónUsar un servicio ajeno que no encaja con el sistema, sin tocar ninguno de los dos"operaciones (que) tienen nombres y formatos diferentes (...) Ese servicio no puede modificarse"Adapter (estructural)
2. Los documentosCrear distintos tipos de documento sin que la mesa de entradas sepa cómo, y poder sumar tipos"para cada tipo de documento existe una oficina con su propio procedimiento para generarlo"Factory Method (creacional)
3. Las sesionesQue haya un solo gestor de sesiones"exista un único gestor de sesiones para toda la aplicación"Singleton (creacional)
Cómo quedaría escrita la respuesta

Adapter, para consultar el padrón. Se usa cuando hay que hacer trabajar juntas dos clases con interfaces incompatibles, sin modificar ninguna, y es el caso: el servicio de la provincia tiene operaciones con "nombres y formatos diferentes" y "no puede modificarse". Se agrega una clase en el medio, el adaptador, que cumple la interfaz con la que los módulos ya consultan los datos de los vecinos y por dentro traduce cada llamada a las operaciones de ese servicio. Así los módulos consultan el padrón igual que cualquier otro dato, sin reescribirlos.

Factory Method, para generar los documentos. Se usa cuando una clase no puede saber de antemano qué tipo exacto de objeto tiene que crear: acá, la mesa de entradas no sabe qué documento le toca (solicitud, reclamo o habilitación). El enunciado lo dice: "Para cada tipo de documento existe una oficina con su propio procedimiento para generarlo". La creación se saca a un método, el método fábrica, que una clase base declara y cada subclase sobrescribe para devolver su documento: hay un creador por cada tipo. Así se agregan tipos nuevos sin modificar el código que los usa, que es lo que se pide: "sin modificar la mesa de entradas".

Singleton, para el control de sesiones. Se usa cuando una clase debe tener una única instancia disponible para todo el programa, y eso pide el enunciado: "exista un único gestor de sesiones para toda la aplicación, de manera que no puedan crearse otros". El gestor de sesiones oculta su constructor y ofrece un método estático que crea el objeto la primera vez y devuelve siempre el mismo. Así todo acceso al sistema pasa por el mismo gestor.

Cada justificación es la descripción del patrón (la del ejemplo 2 de su sección) dicha con las palabras de este enunciado: cuándo se usa, con la frase del enunciado entre comillas; cómo funciona; y qué se gana.

El diagrama de Factory Method. La consigna no lo pide, pero así quedaría dibujada la parte de Factory Method de este enunciado (los nombres de las clases los elige uno):

Oficina es el Creador, con el método fábrica crearDocumento(); cada oficina concreta crea su documento. Documento es el Producto, y MesaDeEntradas, el cliente, trabaja con una Oficina sin saber cuál es.

Las trampas de este enunciado
  • Hay "tipos" de documento, no familias que tengan que combinar: es Factory Method y no Abstract Factory.
  • El primer párrafo no pide simplificar nada: pide hacer encajar un servicio que no se puede tocar. Por eso es Adapter y no Facade.

Ejemplo 5 — Con formato de parcial: reconocerlo en un código

Inventado · con la forma de la Guía N°1, ejercicio 2

"Dado el siguiente código identifique qué tipo de patrón se implementa. Justifique."

Los renglones resaltados son los que lo delatan:

#include <iostream>
#include <string>

class Pasaje {
 public:
  virtual ~Pasaje() {}
  virtual std::string Operation() const = 0;
};

class PasajeAereo : public Pasaje {
 public:
  std::string Operation() const override {
    return "{Pasaje aereo}";
  }
};

class PasajeTerrestre : public Pasaje {
 public:
  std::string Operation() const override {
    return "{Pasaje terrestre}";
  }
};

class Agencia {
 public:
  virtual ~Agencia() {}
  virtual Pasaje* EmitirPasaje() const = 0;

  std::string SomeOperation() const {
    Pasaje* pasaje = this->EmitirPasaje();
    std::string result = "Agencia: se emitio " + pasaje->Operation();
    delete pasaje;
    return result;
  }
};

class AgenciaAerea : public Agencia {
 public:
  Pasaje* EmitirPasaje() const override {
    return new PasajeAereo();
  }
};

class AgenciaTerrestre : public Agencia {
 public:
  Pasaje* EmitirPasaje() const override {
    return new PasajeTerrestre();
  }
};

void ClientCode(const Agencia& agencia) {
  std::cout << agencia.SomeOperation() << "\n";
}

int main() {
  Agencia* aerea = new AgenciaAerea();
  ClientCode(*aerea);
  Agencia* terrestre = new AgenciaTerrestre();
  ClientCode(*terrestre);
  delete aerea;
  delete terrestre;
  return 0;
}
Agencia: se emitio {Pasaje aereo}
Agencia: se emitio {Pasaje terrestre}
RenglónLo que se veQué parte del patrón es
4Una clase con un método virtual puro: la interfaz común de lo que se crea.El Producto
10Clases que heredan de Pasaje y escriben ese método (también PasajeTerrestre).Los Productos Concretos
27Un método virtual puro cuyo tipo de retorno es el Producto.El método fábrica, declarado en el Creador (Agencia)
30El creador llama a su propio método fábrica y usa el producto sin saber cuál es.La lógica del Creador, que no depende del producto concreto

Respuesta: "Es el patrón Factory Method (creacional). Agencia es el creador: declara el método fábrica EmitirPasaje(), que devuelve un Pasaje (el producto), y lo usa en SomeOperation() sin saber qué pasaje recibe. AgenciaAerea y AgenciaTerrestre lo sobrescriben para devolver un PasajeAereo o un PasajeTerrestre. Para sumar otro tipo de pasaje alcanza con una subclase nueva de cada jerarquía."

No confundir con Abstract Factory

Acá hay un solo método de creación y un solo tipo de producto. Si la clase tuviera dos o más métodos de creación que devuelven productos distintos, sería Abstract Factory.

Ejemplo 6 — Con formato de parcial: agregarlo a un diagrama

Inventado · con la forma de la Guía N°1, ejercicio 1

"Dado el siguiente diagrama: la clase Editor crea los documentos dentro de nuevoDocumento(tipo), con un if por cada tipo. Se van a sumar tipos nuevos de documento (presentaciones, PDF) y no se quiere modificar la clase Editor cada vez. Modifique el diagrama aplicando el patrón de diseño que corresponda. Justifique."

Qué hay en el diagrama. Editor depende de dos clases concretas: las dos flechas "crea" van directo a DocumentoTexto y a DocumentoPlanilla. Cada tipo nuevo sería otra flecha y otro if. Las dos clases de documento tienen los mismos métodos, pero nada dice que sean del mismo tipo.

Qué se cambia, en orden:

  1. Crear la interfaz Producto. Documento, con los métodos que comparten (abrir(), guardar()). DocumentoTexto y DocumentoPlanilla la cumplen: línea punteada con triángulo.
  2. Convertir la creación en el método fábrica. En Editor se agrega crearDocumento(): Documento, abstracto (en cursiva), y Editor pasa a ser una clase abstracta. nuevoDocumento() se queda en Editor: ahora llama a crearDocumento() y ya no necesita el parámetro tipo.
  3. Agregar un creador concreto por cada producto. EditorDeTexto y EditorDePlanillas, que heredan de Editor (línea continua con triángulo) y sobrescriben crearDocumento().
  4. Cambiar las flechas de creación. Se borran las dos que iban de Editor a las clases concretas y queda una sola, punteada, de Editor a la interfaz Documento.

El diagrama modificado:

Justificación: "Se aplica Factory Method porque Editor no puede saber de antemano qué tipo exacto de documento tiene que crear, y se van a sumar tipos. La creación se saca a un método, el método fábrica crearDocumento(), que Editor declara y cada subclase (EditorDeTexto y EditorDePlanillas) sobrescribe para devolver su documento. Así se agregan tipos nuevos sin modificar Editor ni los documentos que ya existen."

A tener en cuenta al modificar el diagrama
  • Van dos jerarquías en paralelo: un creador concreto por cada producto concreto.
  • El método que usa el producto (nuevoDocumento()) queda en el creador: no se borra ni baja a las subclases.
  • Los creadores heredan (línea continua: Editor es una clase); los productos realizan (línea punteada: Documento es una interfaz).
  • La flecha "crea" llega a la interfaz Documento, nunca a un documento concreto.

Errores y trampas

No es "una clase con un if que decide qué crear"

Una función con un switch que devuelve un camión o un barco según un parámetro todavía obliga a modificarla cada vez que aparece un tipo nuevo. En Factory Method la decisión está en qué subclase creadora se usa, y para un tipo nuevo se agrega una subclase.

En el dibujo, no olvidar la interfaz del producto

Sin la interfaz Producto, el Creador tendría que nombrar a las clases concretas y el patrón pierde sentido. El método fábrica devuelve la interfaz.
