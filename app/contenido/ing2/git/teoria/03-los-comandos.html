Git

3. Los comandos: del directorio de trabajo al remoto

Para qué sirve

Cada comando de Git mueve cambios de un lugar a otro del mapa de la sección 2. Con siete comandos se resuelve la pregunta del parcial: add, commit, checkout, branch, merge, push y pull. 

Directorio        Área de          Repositorio         Repositorio
de trabajo        preparación      local               remoto (origin)

    │── git add ──────▶│                │                    │
    │                  │── git commit ─▶│                    │
    │                  │                │──── git push ─────▶│
    │◀───────────────── git pull ────────────────────────────│

Conceptos fundamentales

ConceptoQué es
CommitUna "captura" de los cambios del proyecto en un momento: una unidad de cambio que guarda una versión del código, con un mensaje que explica su propósito. Los commits forman el historial.
Branch (rama)Una versión paralela del proyecto. Permite trabajar en algo nuevo o en una corrección sin afectar la rama principal (llamada main o master).
Merge (fusión)El proceso de combinar los cambios de distintas ramas en una sola. Es automático si no hay conflictos.
Pull request (PR)Una solicitud para que los cambios de una rama sean revisados e integrados en otra. Se hace en la plataforma (GitHub, GitLab, Bitbucket), no con un comando: permite revisar, discutir y aprobar antes de integrar.
Remoto (origin)La copia del repositorio que está en el servidor y comparte el equipo. origin es el nombre que Git le pone por defecto.

El apunte desarrolla todos menos git pull, que es el inverso de push y se usa para arrancar con la última versión de lo que subieron los demás.

Ignorar archivos: un archivo llamado .gitignore lista patrones de archivos que Git no tiene que seguir (por ejemplo, los que genera el compilador).

Ejemplo 2 — Con formato de parcial: de Working Directory a develop y a main

Parcial 2025 · Teoría 3 (5 puntos)

"Indique los pasos que debe seguir el equipo de desarrollo para registrar todos los cambios del código desde el Working Directory hacia la rama develop, y luego integrarlos en main, asegurando que ambas ramas estén actualizadas en el remoto (Git Workflow)."

Paso 1 — Desarme de la consigna. Cada frase es un tramo del mapa.

Frase de la consignaQué significaComando
"registrar todos los cambios (...) desde el Working Directory"Preparar todo lo modificado y confirmarlogit add . y git commit
"hacia la rama develop"Hay que estar parado en develop al confirmargit checkout develop
"y luego integrarlos en main"Pasar a main y fusionarle developgit checkout main y git merge develop
"asegurando que ambas ramas estén actualizadas en el remoto"Subir las dosgit push origin develop y git push origin main

develop es la rama donde se junta el trabajo en desarrollo; main, la rama principal, con lo que está listo. Git Workflow es "flujo de trabajo con Git": la secuencia de pasos que sigue el equipo.

Paso 2 — La secuencia.

git checkout develop
git add .
git commit -m "Descripción de los cambios"
git push origin develop
git checkout main
git merge develop
git push origin main

Qué responde Git

Ejecutado en un repositorio de prueba (se cambió index.html y se creó estilos.css):

$ git commit -m "Cambia el titulo y agrega estilos"
[develop c11a3b1] Cambia el titulo y agrega estilos
 2 files changed, 2 insertions(+), 1 deletion(-)
 create mode 100644 estilos.css

$ git push origin develop
   6d83081..c11a3b1  develop -> develop

$ git merge develop
Updating 6d83081..c11a3b1
Fast-forward
 estilos.css | 1 +
 index.html  | 2 +-

$ git push origin main
   6d83081..c11a3b1  main -> main

Y al final, git log --oneline --all --decorate confirma que quedó todo igual:

c11a3b1 (HEAD -> main, origin/main, origin/develop, develop) Cambia el titulo y agrega estilos
6d83081 Version inicial
  • main y develop: las dos ramas locales apuntan al mismo commit.
  • origin/main y origin/develop: las dos ramas del remoto también. Ambas actualizadas en el remoto, como pedía la consigna.
  • Fast-forward: como main no tenía commits propios, Git solo adelantó main hasta donde estaba develop.
Cómo quedaría escrita la respuesta
  1. Ubicarse en la rama de desarrollo: git checkout develop.
  2. Pasar los cambios del Working Directory al área de preparación: git add .
  3. Confirmarlos en el repositorio local: git commit -m "mensaje".
  4. Subir develop al remoto: git push origin develop.
  5. Cambiar a la rama principal: git checkout main.
  6. Integrar los cambios de develop: git merge develop.
  7. Subir main al remoto: git push origin main.

Con eso los cambios pasaron por Working Directory → Staging Area → repositorio local → remoto, y las dos ramas quedaron actualizadas.

Lo que se puede agregar para una respuesta más completa
  • git pull origin develop antes de empezar, y git pull origin main antes del merge: traen lo que hayan subido los compañeros, para no integrar sobre una versión vieja.
  • git status antes del add, para ver qué cambió.
  • En un equipo, el paso de develop a main muchas veces se hace con un pull request en la plataforma, para que alguien revise antes de integrar.

Errores y trampas

El merge se hace parado en la rama que recibe

git merge develop trae develop hacia donde estoy. Para integrar en main hay que hacer primero git checkout main. El error típico es hacer el merge sin cambiar de rama.

Dos push, no uno

La consigna dice "ambas ramas". git push origin main sube solo main. Si falta el push de develop, en el remoto esa rama queda vieja.

Sin add no hay nada que confirmar

git commit guarda solo lo que está en el área de preparación. Saltearse el add es saltearse un estado: la consigna arranca "desde el Working Directory" justamente para que aparezcan los tres.
