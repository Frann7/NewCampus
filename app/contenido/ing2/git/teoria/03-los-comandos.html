Git

3. Los comandos: del directorio de trabajo al remoto

Para qué sirve

Cada comando de Git mueve cambios de un lugar a otro del mapa de la sección 2. Con siete comandos se resuelve la pregunta del parcial: add, commit, checkout, branch, merge, push y pull.

Conceptos fundamentales

ConceptoQué es
CommitUna "captura" de los cambios del proyecto en un momento: una unidad de cambio que guarda una versión del código, con un mensaje que explica su propósito. Los commits forman el historial.
Branch (rama)Una versión paralela del proyecto. Permite trabajar en algo nuevo o en una corrección sin afectar la rama principal (llamada main o master).
Merge (fusión)El proceso de combinar los cambios de distintas ramas en una sola. Es automático si no hay conflictos.
Pull request (PR)Una solicitud para que los cambios de una rama sean revisados e integrados en otra. Se hace en la plataforma (GitHub, GitLab, Bitbucket), no con un comando: permite revisar, discutir y aprobar antes de integrar.
Remoto (origin)La copia del repositorio que está en el servidor y comparte el equipo. origin es el nombre que Git le pone por defecto.

Una rama y su merge, dibujados: cada círculo es un commit. La rama funcion sale de main, suma sus commits sin tocar la principal y vuelve a ella con un merge, que crea un commit nuevo (M) con los cambios de las dos.

El apunte desarrolla todos menos git pull, que es el inverso de push y se usa para arrancar con la última versión de lo que subieron los demás.

Ignorar archivos: un archivo llamado .gitignore lista patrones de archivos que Git no tiene que seguir (por ejemplo, los que genera el compilador).

Ejemplo 2 — Con formato de parcial: de Working Directory a testing y a master

Inventado · con la forma del Parcial 2025, Teoría 3

"Un equipo trabaja con dos ramas: testing, donde junta lo que desarrolla, y master, que es la versión estable. Indique los pasos que debe seguir para registrar todos los cambios del código desde el Working Directory hacia la rama testing, y luego integrarlos en master, asegurando que ambas ramas estén actualizadas en el remoto."

Paso 1 — Desarme de la consigna. Cada frase es un tramo del mapa.

Frase de la consignaQué significaComando
"registrar todos los cambios (...) desde el Working Directory"Preparar todo lo modificado y confirmarlogit add . y git commit
"hacia la rama testing"Hay que estar parado en testing al confirmargit checkout testing
"y luego integrarlos en master"Pasar a master y fusionarle testinggit checkout master y git merge testing
"asegurando que ambas ramas estén actualizadas en el remoto"Subir las dosgit push origin testing y git push origin master

testing es la rama donde se junta el trabajo en desarrollo; master, la rama principal, con lo que está listo. Git Workflow es "flujo de trabajo con Git": la secuencia de pasos que sigue el equipo.

Paso 2 — La secuencia.

git checkout testing
git add .
git commit -m "Descripción de los cambios"
git push origin testing
git checkout master
git merge testing
git push origin master

Qué responde Git

Ejecutado en un repositorio de prueba (se cambió index.html y se creó estilos.css):

$ git commit -m "Cambia el titulo y agrega estilos"
[testing c11a3b1] Cambia el titulo y agrega estilos
 2 files changed, 2 insertions(+), 1 deletion(-)
 create mode 100644 estilos.css

$ git push origin testing
   6d83081..c11a3b1  testing -> testing

$ git merge testing
Updating 6d83081..c11a3b1
Fast-forward
 estilos.css | 1 +
 index.html  | 2 +-

$ git push origin master
   6d83081..c11a3b1  master -> master

Y al final, git log --oneline --all --decorate confirma que quedó todo igual:

c11a3b1 (HEAD -> master, origin/master, origin/testing, testing) Cambia el titulo y agrega estilos
6d83081 Version inicial
  • master y testing: las dos ramas locales apuntan al mismo commit.
  • origin/master y origin/testing: las dos ramas del remoto también. Ambas actualizadas en el remoto, como pedía la consigna.
  • Fast-forward: como master no tenía commits propios, Git solo adelantó master hasta donde estaba testing.
Cómo quedaría escrita la respuesta
  1. Ubicarse en la rama de desarrollo: git checkout testing.
  2. Pasar los cambios del Working Directory al área de preparación: git add .
  3. Confirmarlos en el repositorio local: git commit -m "mensaje".
  4. Subir testing al remoto: git push origin testing.
  5. Cambiar a la rama principal: git checkout master.
  6. Integrar los cambios de testing: git merge testing.
  7. Subir master al remoto: git push origin master.

Con eso los cambios pasaron por Working Directory → Staging Area → repositorio local → remoto, y las dos ramas quedaron actualizadas.

Lo que se puede agregar para una respuesta más completa
  • git pull origin testing antes de empezar, y git pull origin master antes del merge: traen lo que hayan subido los compañeros, para no integrar sobre una versión vieja.
  • git status antes del add, para ver qué cambió.
  • En un equipo, el paso de testing a master muchas veces se hace con un pull request en la plataforma, para que alguien revise antes de integrar.

Errores y trampas

El merge se hace parado en la rama que recibe

git merge testing trae testing hacia donde estoy. Para integrar en master hay que hacer primero git checkout master. El error típico es hacer el merge sin cambiar de rama.

Dos push, no uno

La consigna dice "ambas ramas". git push origin master sube solo master. Si falta el push de testing, en el remoto esa rama queda vieja.

Sin add no hay nada que confirmar

git commit guarda solo lo que está en el área de preparación. Saltearse el add es saltearse un estado: la consigna arranca "desde el Working Directory" justamente para que aparezcan los tres.
